Swap the algorithm at runtime

Real-world picture: a maps app planning the same trip. Tap “drive,” “bike,” or “walk” and it runs a different routing algorithm — but the app around it doesn’t change. Strategy defines a family of interchangeable algorithms and lets you pick one at runtime.

Concept

Algorithms behind a common interface

🏷 Real-world analogy

A strategy is a GPS route setting. Your destination is fixed — the context of the trip never changes — but you get to choose the algorithm that plans the way there: fastest, shortest, or avoid tolls. Each setting is a self-contained way of computing a route, and they are perfectly interchangeable: the navigator does not care which one is active. Tap a different setting mid-trip and it swaps at runtime — the navigator just re-runs whichever strategy you plugged in, no rewiring of the app around it. That is Strategy: the context (navigator) holds a pluggable algorithm behind one interface, and you decide which implementation it runs.

When you find a big switch choosing between behaviors, Strategy is usually the fix. Each behavior becomes a class implementing a shared interface; the context holds one and delegates to it. Swapping behavior is now a setter call, not an edit.

Because Java lambdas are implementations of single-method interfaces, Strategy often collapses to passing a function: list.sort(Comparator.comparing(User::age)) passes a sorting strategy. It’s the runtime-flexible cousin of polymorphism, and it powers pricing rules, validators, and compression choices everywhere.

    


    
Intent: a family of interchangeable algorithms

    
The Gang of Four define Strategy as: define a family of algorithms, encapsulate each one, and make them interchangeable. The point is to let the algorithm vary independently of the client that uses it. The context is programmed against the interface, never a concrete implementation — so it is not hard-wired to any one algorithm and new ones can be added without touching it.



    
Replacing a sprawling switch on a “type”

    
The classic smell that Strategy cures is a growing switch or if/else chain that branches on some “kind” field. Every new kind forces you to reopen and edit the method — a violation of the Open/Closed Principle. Strategy turns each branch into its own polymorphic object; the branch selection happens once, at the edge, when you pick the strategy.



    
The modern Java form: a lambda is the strategy

    
A strategy interface almost always has a single abstract method, which makes it a @FunctionalInterface. That means you rarely write a named implementation class at all: a lambda or method reference already is an instance of the interface. The boilerplate of one class per algorithm collapses into an expression, while the pattern — pluggable behavior behind an interface — is unchanged.



    
The canonical JDK example: Comparator

    
You have used Strategy for years without naming it. Comparator<T> passed to Collections.sort, List.sort, or Stream.sorted is a sorting strategy: the sort algorithm is fixed, but the ordering it uses is a pluggable object you supply. Runnable (the task a thread runs) and Function (a mapping applied by Stream.map) are strategies in the same spirit.



    
Injecting one strategy, selecting from many

    
A context usually receives its strategy through the constructor (or DI framework), which keeps it immutable and testable; a mutable setter is only needed when the algorithm must change during an object’s life. When the choice is data-driven — a config value, a user click, a request field — register the strategies in a Map<String, Strategy> and look one up, instead of branching.



    
Strategy vs State: same shape, different intent

    
Strategy and State (module 45) have an identical class diagram — a context delegating to an object behind an interface — which is why they are so often confused. The difference is intent. In Strategy, the client picks the algorithm and it typically stays put; the strategies are unaware of each other and vary how one operation is done. In State, the objects represent phases of a lifecycle, they carry internal state, and they swap themselves as transitions happen — the behavior changes as the object’s internal state changes.

Coming from another language

    
What will surprise you

      
Coming from Python
Functions are first-class, so a strategy is usually just a function you pass in: sorted(items, key=by_age). Java reaches the same place with lambdas, which are shorthand for single-method strategy interfaces.

      
Coming from JavaScript
Pass a callback — arr.sort((a,b) => a.age - b.age) — and you’ve used Strategy. Java’s Comparator lambdas are the exact analog.

      
Coming from C#
Func<>/Action<> delegates are strategies passed as values, just like Java lambdas. LINQ’s OrderBy(keySelector) is Strategy in action.

  






  

    
Exercises

    
Make it stick

      
1 · Refactor the switch
You see switch(type){ case CARD: ...; case PAYPAL: ...; } for payments. How does Strategy improve it?
💡 Show hint
Make a PaymentStrategy interface with one implementation per method; the context holds and calls one. Adding a payment type means adding a class, not editing the switch (also satisfies Open/Closed from module 12).

      
2 · Lambda or class?
When is a full Strategy class better than passing a lambda?
💡 Show hint
A lambda is perfect for a small, stateless one-off. Prefer a named class when the strategy has state/config, needs a good name, is reused in many places, or is complex enough to test on its own.

      
3 · Name the JDK strategy
Which everyday JDK type do you pass to list.sort(...), and why is it a textbook Strategy?
💡 Show hint
Comparator<T>. The sort algorithm is fixed inside sort, but the ordering is a pluggable object you supply — and because it is a functional interface you usually pass a lambda like Comparator.comparing(User::age). Same context, swappable algorithm.

      
4 · Strategy or State?
A traffic light cycles green→amber→red→green, each phase deciding what happens next. Is that Strategy or State?
💡 Show hint
State. The objects represent phases of a lifecycle and transition themselves as events occur, with behavior driven by internal state. Strategy would be the light asking you to pick one fixed algorithm and sticking with it — the two share a class diagram but differ in intent.

      
5 · Select without a switch
A request carries a string like "SAVE10" that must choose a discount algorithm. How do you pick the strategy at runtime without an if/else chain?
💡 Show hint
Register the strategies once in a Map<String, DiscountStrategy> and do map.getOrDefault(code, DEFAULT). Selection becomes a lookup, adding a strategy becomes a map entry, and the context still just calls apply(...) on whatever it got.
