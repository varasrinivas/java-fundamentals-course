The green bar that lets you refactor fearlessly

JUnit is so central it ships in muscle memory: annotate a method @Test, arrange-act-assert, run. Add AssertJ for readable assertions and Mockito for fakes, and you have the safety net behind every confident Java change.

Concept

Arrange, act, assert — one behavior per test

🏭 Real-world analogy

A test suite is a factory’s quality-control line. Each unit test is an inspector at one station: it feeds a single part a known input, then checks the output against the spec — that check is an assertion. To test one station without spinning up the whole assembly line, the inspector slots in a mock — a stand-in dummy part that behaves exactly as told, so a failure can only mean this station is broken. When every inspector signs off, the line shows a green sign-off (the green bar) and the product is cleared to ship. A red light halts the line at the exact station that failed, so you never ship a defect you could have caught for a fraction of a cent.

A test is a method marked @Test. The runner finds it by that annotation, runs it in isolation, and reports pass or fail. The classic shape is arrange (set up inputs), act (call the thing), assert (check the result).

Good tests are fast, independent, and named for the behavior they pin down. The payoff: a passing suite turns a scary refactor into a routine one — change the code, run the bar, trust the result.

    

    
    
JUnit 5 basics: @Test and assertThrows

    
JUnit 5 (the org.junit.jupiter packages) is the default. A test is any method annotated @Test — it needs no public modifier and takes no arguments. The static helpers on Assertions (usually imported statically) do the checking: assertEquals(expected, actual), assertTrue, assertNull, and assertThrows for the exception path.




    
Lifecycle hooks: @BeforeEach and friends

    
Duplicated setup moves into lifecycle methods. @BeforeEach runs before every test method, giving each one a fresh fixture — crucial because JUnit constructs a new instance of the test class for each test, so instance fields never leak between tests. @AfterEach cleans up. The @BeforeAll/@AfterAll pair runs once for the whole class and must be static (there is no instance yet), so reserve them for expensive shared resources like a test container.




    
Parameterized tests & @DisplayName

    
When one behavior should hold across many inputs, don’t copy-paste. A @ParameterizedTest runs the same body once per value. Feed it with @ValueSource for a single-column list, or @CsvSource when each case needs input and expected output. Add @DisplayName (or a name template) so reports read as sentences instead of method names.




    
The testing pyramid — and what a “unit” is

    
The testing pyramid is a guideline for proportions: a wide base of unit tests (many, milliseconds each), a thinner band of integration tests (fewer, exercising real wiring like a database), and a narrow tip of end-to-end tests (few, slow, driving the whole system). A unit isn’t necessarily one class — it’s one behavior tested in isolation from slow or nondeterministic collaborators. Invert the pyramid (mostly e2e) and your suite becomes slow and flaky; that shape is nicknamed the “ice-cream cone”.




    
Test doubles & mocking with Mockito

    
To test a class in isolation you replace its collaborators with test doubles. Mockito’s mock(Type.class) creates a fake whose methods return defaults until you stub them with when(...).thenReturn(...). After acting, verify(...) asserts an interaction actually happened. Stub queries (things you read) and verify commands (side effects you care about) — over-verifying couples the test to implementation detail.




    
Good tests & fluent AssertJ

    
A good unit test is fast (no I/O), isolated (order-independent), deterministic (same result every run — no wall clock or random seed), and has one reason to fail. Test behavior, not implementation: assert on observable outcomes, not private fields, so refactors don’t break green tests. AssertJ makes the assertion side read like prose — one assertThat entry point, discoverable chained matchers, and far clearer failure messages than raw assertEquals.

Coming from another language

    
What will surprise you

      
Coming from Python
JUnit is pytest's heavier, annotation-driven cousin: @Test instead of a test_ name prefix, assertEquals(a, b) instead of bare assert a == b. AssertJ closes the readability gap.

      
Coming from JavaScript
@Test methods replace it(...) blocks; @BeforeEach is beforeEach. Mockito plays the role of Jest's mocking. The arrange-act-assert rhythm is identical to describe/it suites.

      
Coming from C#
JUnit maps almost one-to-one onto xUnit/NUnit: @Test ≈ [Fact]/[Test], @BeforeEach ≈ setup. Mockito ≈ Moq, AssertJ ≈ FluentAssertions. If you've tested in C#, you already test in Java.

  






  

    
Exercises

    
Make it stick

      
1 · Expected vs actual
In assertEquals(5, sum), which argument is the expected value and why does the order matter for the failure message?
💡 Show hint
The first argument is expected, the second actual. JUnit's message reads “expected: 5 but was: …”, so swapping them produces a misleading report even though the pass/fail result is the same.

      
2 · Why isolate?
Why should each @Test be independent of the others, and what tool helps when a test has external collaborators?
💡 Show hint
Independent tests can run in any order and in parallel, and a failure points at one cause. For external collaborators (a DB, a service), use a mocking library like Mockito to supply fast, deterministic fakes.

      
3 · assertThrows over try/catch
You want to test that parse("") throws an IllegalArgumentException. Why is assertThrows better than wrapping the call in a try/catch with a fail()?
💡 Show hint
assertThrows(IllegalArgumentException.class, () -> parse("")) fails automatically if nothing is thrown, returns the exception so you can assert on its message, and reads in one line. A hand-rolled try/catch needs an explicit fail() after the call (easy to forget) and is far noisier.

      
4 · @BeforeEach vs @BeforeAll
A field set in @BeforeAll must be static, but one set in @BeforeEach need not be. Why the difference, and which should hold a fresh ArrayList fixture per test?
💡 Show hint
JUnit creates a new instance of the test class for every @Test, so @BeforeAll runs before any instance exists and must be static. A per-test fresh ArrayList belongs in @BeforeEach so tests can’t pollute each other’s state.

      
5 · Stub vs verify
Given a mocked PriceApi and AuditLog, which one do you set up with when(...).thenReturn(...) and which with verify(...)? What’s the general rule?
💡 Show hint
Stub queries, verify commands. PriceApi is a query you read a value from, so stub it with when(priceApi.priceOf(x)).thenReturn(9.99). AuditLog is a command with a side effect, so assert it happened with verify(auditLog).record(...). Verifying queries or stubbing commands over-couples the test to implementation.
