Five rules for classes that don’t rot

SOLID is five design principles that keep object-oriented code flexible as it grows. They tie together everything in this track — encapsulation, polymorphism, composition, interfaces, and dependency injection — into a checklist for classes that survive change.

Concept

S · O · L · I · D

🏗 Real-world analogy

SOLID is the building code for software. A city’s building code is a set of construction rules that keep a structure safe and livable as it grows and gets renovated. Each SOLID letter is one such rule. Single Responsibility is “one room, one purpose” — the kitchen isn’t also the electrical panel. Open/Closed is “add an extension without knocking down load-bearing walls.” Liskov Substitution is “any certified fixture can be swapped for another of the same rating” — a replacement outlet must behave like an outlet. Interface Segregation is “don’t force every tenant to pay for a pool and a gym they never use.” Dependency Inversion is “plug appliances into standardized sockets, not directly into the wiring in the wall.” Follow the code and the building keeps standing through decades of change; ignore it and every renovation risks the whole structure.

S — Single Responsibility: a class should have one reason to change. A class that parses and validates and saves is three classes wearing a trench coat.

O — Open/Closed: open for extension, closed for modification. Add behavior by adding a new type (a new Shape implementation), not by editing a giant switch.

L — Liskov Substitution: a subtype must be usable anywhere its supertype is, without surprises. If Square extends Rectangle breaks code that sets width and height independently, you’ve violated it.

I — Interface Segregation: prefer many small interfaces over one fat one. Don’t force a class to implement methods it doesn’t need.

D — Dependency Inversion: depend on abstractions, not concretions. High-level code should rely on an interface and have the implementation injected (see the DI module).


    


    
S — Single Responsibility

    
A class should have one reason to change — that is, answer to a single actor or concern. When formatting, persistence, and messaging all live in one class, a change to any of the three risks the other two, and the class becomes a merge-conflict magnet. The fix is to give each concern its own class and let a coordinator wire them together.

    
“One reason to change” is subtler than “one method”: it’s about who asks for the change. The renderer changes when marketing wants new HTML; the repository changes when the DBA alters schema. Different masters → different classes.

    

    
O — Open/Closed

    
Software entities should be open for extension but closed for modification. You should be able to add new behavior by adding new code (a new type or strategy), not by editing existing, already-tested code. A growing if/instanceof chain or switch that you edit for every new case is the classic smell.

    
In Java the lever is polymorphism: define an interface, and let each new case be a new implementation. Existing methods never change, so existing tests stay green and can’t regress.

    

    
L — Liskov Substitution

    
Subtypes must be usable through the base type without surprises: anywhere the code expects a Rectangle, handing it a subtype must not break the caller’s assumptions. The classic trap is Square extends Rectangle — mathematically a square is a rectangle, but overriding the setters to keep sides equal violates the base class’s contract that width and height move independently.

    
Another form is the Bird/Penguin trap: if Bird promises fly() and Penguin throws from it, penguins aren’t substitutable birds. LSP is really about honoring contracts — preconditions no stronger, postconditions no weaker than the base type’s.

    

    
I — Interface Segregation

    
Many small, role-focused interfaces beat one fat interface. No client should be forced to depend on methods it doesn’t use. The tell-tale sign of a violation is an implementation that has to write throw new UnsupportedOperationException() for a method that makes no sense for it.

    
Java’s standard library learned this lesson: interfaces like Runnable, Comparable, and AutoCloseable each declare a single method, so a class implements exactly the roles it actually plays.

    

    
D — Dependency Inversion

    
High-level code should depend on abstractions, not on low-level details. Both should depend on interfaces. Concretely: don’t new up a database class inside your business logic — accept an interface and let the caller inject the implementation. This inverts the usual compile-time arrow so the policy no longer imports the plumbing.

    
Injecting the dependency (constructor injection is the Java idiom) makes the high-level class testable with a fake and reconfigurable in production — exactly what frameworks like Spring automate. DIP is the principle; dependency injection is the technique that delivers it.

Coming from another language

    
What will surprise you

      
Coming from Python
SOLID is language-agnostic and applies to Python too, though duck typing softens ISP and DIP (you depend on a shape of object, not a declared interface). The SRP and OCP advice carries over unchanged.

      
Coming from JavaScript
The same principles guide JS/TS design; DIP shows up as passing dependencies into functions/constructors rather than importing concretes. TypeScript interfaces make ISP and DIP feel very Java-like.

      
Coming from C#
SOLID grew up largely in the C#/Java OO world, so it maps directly — interfaces, virtual/override for LSP, and built-in DI containers for DIP. Same checklist, same payoff.

  






  

    
Exercises

    
Make it stick

      
1 · Name the violation
A Report class formats HTML, queries the database, and emails the result. Which SOLID letter does it break, and how do you fix it?
💡 Show hint
S (Single Responsibility) — it has three reasons to change. Split it into a formatter, a repository, and a mailer, each with one job, and coordinate them (often via injected dependencies, which also serves D).

      
2 · Open/Closed in practice
Adding each new payment type means editing a growing switch(type). Which principle is strained, and what’s the OO fix?
💡 Show hint
O (Open/Closed). Replace the switch with a PaymentMethod interface and one implementation per type; adding a payment means adding a class, not modifying existing, tested code (polymorphism doing the dispatch).

      
3 · The Square/Rectangle trap
Why is class Square extends Rectangle — with overridden setters that keep all sides equal — a Liskov violation, even though a square really is a kind of rectangle?
💡 Show hint
L (Liskov Substitution). Rectangle’s contract lets a caller set width and height independently; Square secretly changes both, so code like setWidth(5); setHeight(4); assert area()==20 fails for a Square. The subtype strengthens an implicit precondition and surprises callers. Fix: don’t inherit — model them as separate (often immutable) shapes.

      
4 · Spot the fat interface
A Machine interface declares print(), scan(), and fax(). Your SimplePrinter can only print, so its scan() and fax() throw UnsupportedOperationException. Which principle is violated and how do you fix it?
💡 Show hint
I (Interface Segregation). The forced UnsupportedOperationException is the giveaway. Split Machine into small role interfaces — Printer, Scanner, Fax — and let SimplePrinter implement only Printer. A multifunction device implements all three.

      
5 · Invert the dependency
A NotificationService does new SmtpEmailSender() inside its constructor. It works, but it’s hard to unit-test and you can’t switch to SMS. Which principle is broken, and what’s the idiomatic Java fix?
💡 Show hint
D (Dependency Inversion). The high-level service imports a low-level concrete class. Define a MessageSender interface, have NotificationService accept it via constructor injection, and let the caller (or a DI container like Spring) supply SmtpEmailSender in production and a fake in tests.
