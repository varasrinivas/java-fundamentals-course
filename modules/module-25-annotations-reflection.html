Metadata the code can read about itself

Annotations attach metadata to code; reflection reads classes, fields, and methods at runtime. Together they power the frameworks you'll actually use — Spring, JUnit, Jackson — which wire things up by inspecting your annotated types.

Concept

Tags on code, and an API to inspect them

🏷 Real-world analogy

Annotations are luggage tags; reflection is a pair of X-ray goggles. An annotation is a sticky note you staple to a class, field, or method — @Test, @Deprecated, @JsonProperty. The tag carries no behavior of its own; it just sits there as metadata until some tool or framework walks by, reads it, and decides what to do. Reflection is the X-ray goggles a running program puts on to look inside its own classes — enumerating fields and methods, reading those tags, and even reaching in to read a private value or call a method by name, without the compiler ever knowing that name existed. A framework like Spring or JUnit wears the goggles, spots your tags, and wires everything up for you.

An annotation like @Override or @Test is metadata. Its @Retention says how long it survives: SOURCE (compiler only), CLASS (in bytecode), or RUNTIME (readable while running). Reflection is the API that reads types at runtime and can act on those annotations.

This is how a serializer maps name to "full_name", how JUnit finds @Test methods, and how Spring injects beans — all without you wiring it by hand. Reflection is powerful but slower and bypasses compile-time checks, so use it through frameworks, not as a default tool.

    
Annotations are metadata — the built-ins do nothing on their own

    
An annotation is just data attached to a program element. On its own it changes nothing at runtime; something has to read it. The JDK ships a handful whose “reader” is the compiler itself: @Override makes the compiler verify you actually override a supertype method (a typo becomes an error, not a silent new method); @Deprecated emits a warning at every use site; @SuppressWarnings silences specific compiler warnings in its scope; and @FunctionalInterface asserts the interface has exactly one abstract method so lambdas stay valid.

    


    
Retention: SOURCE, CLASS, RUNTIME — only RUNTIME is visible to reflection

    
@Retention decides how long an annotation survives. SOURCE is discarded by the compiler (e.g. @Override) — useful only to source tools. CLASS (the default) is written into the .class file but not loaded by the JVM, so reflection can’t see it. Only RUNTIME is kept in memory and readable via reflection — which is why every framework annotation you inspect at run time is marked RUNTIME. A separate @Target restricts where the annotation may be placed (types, methods, fields, parameters…), turning misuse into a compile error.

    


    
Defining a custom annotation with elements and defaults

    
You declare one with @interface. Its elements look like no-arg methods; each may have a default. Element types are limited to primitives, String, Class, enums, other annotations, and arrays of those. A single element named value can be supplied without naming it (@Column("id") instead of @Column(value = "id")).

    


    
The reflection API: Class, fields, methods, invoke

    
Every object can hand you its Class object — the entry point to reflection — via obj.getClass() or the literal Type.class. From there, getDeclaredFields() and getDeclaredMethods() enumerate members declared on this class (including private ones; the non-Declared variants return only public members, but include inherited ones). Field.get/set read and write values; Method.invoke calls a method by name. Private members require setAccessible(true) first — the switch that lets reflection defeat access control.

    


    
How frameworks combine the two

    
Almost every “magic” framework is the same recipe: scan for annotated members, then act via reflection. JUnit reflects over your test class, finds methods tagged @Test, and invokes each. Spring scans beans for @Autowired fields and reflectively injects dependencies. Jackson reads @JsonProperty to map a field to a differently named JSON key while (de)serializing. You write declarative tags; the framework supplies the loop that reads and acts on them.

    


    
The costs: reflection is slower and unsafe

    
Reflection is powerful precisely because it escapes the guarantees you normally rely on. It bypasses compile-time checks: a mistyped method name or wrong argument type becomes a runtime NoSuchMethodException or ClassCastException, not a red squiggle. It is slower than a direct call (member lookups, boxing of primitives, security checks — though the JIT recovers much of it on hot paths). And setAccessible(true) breaks encapsulation, reaching into private state the class never meant to expose — and on modern Java the module system can slam that door with an InaccessibleObjectException. Rule of thumb: let frameworks use it; in your own code, prefer an interface, a lambda, or a plain method call.

Coming from another language

    
What will surprise you

      
Coming from Python
Reflection is Python's everyday getattr/dir/inspect, and annotations are like decorators plus __annotations__. Java's version is more ceremonious and type-checked, but the framework-magic use cases are identical.

      
Coming from JavaScript
Closest to JS decorators (TC39 / TypeScript) plus Reflect and Object.keys. Java annotations are declarative metadata read via a rich reflection API — the engine behind Spring/JUnit much like decorators power Angular/Nest.

      
Coming from C#
Annotations are C# attributes, and reflection maps almost one-to-one (typeof(T), GetFields(), GetCustomAttribute). If you've used attributes to drive serialization or DI in .NET, Java works the same way.

  






  

    
Exercises

    
Make it stick

      
1 · Why RUNTIME retention?
Your custom annotation is read by a framework while the app runs, but it “isn't there” reflectively. What's the likely cause?
💡 Show hint
Its @Retention is the default (CLASS) or SOURCE, so it isn't kept for runtime. Add @Retention(RetentionPolicy.RUNTIME) so reflection can see it.

      
2 · Reflection has a cost
Reflection can call any method by name at runtime. Name one downside that makes it a last resort for everyday code.
💡 Show hint
It bypasses compile-time type checking (errors surface at runtime), is slower than direct calls, and can break encapsulation. Great for frameworks; avoid it when a normal method call or interface would do.

      
3 · Read a private field
You have a Point with a private int x. Sketch the reflection calls to read x from an instance p. What one call must you not forget?
💡 Show hint
Field f = p.getClass().getDeclaredField("x"); then f.setAccessible(true); then int x = (int) f.get(p);. Without setAccessible(true) the private field throws IllegalAccessException (and on a locked-down module, InaccessibleObjectException).

      
4 · @Override on a typo
You meant to override toString() but wrote toStrng(). How does adding @Override save you, and what happens without it?
💡 Show hint
With @Override the compiler checks that a matching supertype method exists; the typo doesn't, so you get a compile error. Without it, toStrng() silently becomes a brand-new, never-called method and the real toString() still runs — a bug that ships. This is exactly the “annotation read by the compiler” case.

      
5 · Design a @Column
Define a custom @Column annotation an ORM could read at runtime: it needs a column name and an optional “not null” flag defaulting to allowing nulls. Which meta-annotations and elements do you write?
💡 Show hint
Mark it @Retention(RetentionPolicy.RUNTIME) (so the ORM's reflection can see it) and @Target(ElementType.FIELD). Declare String value(); for the name (positional) and boolean nullable() default true; for the optional flag. Use as @Column("email") or @Column(value="email", nullable=false).
