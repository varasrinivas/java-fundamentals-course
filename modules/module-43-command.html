Wrap a request as an object

Real-world picture: a restaurant order ticket. The waiter writes your request on a slip and hangs it in the kitchen. The slip is a thing — it can be queued, reordered, and even cancelled. Command turns an action into an object you can store, pass around, queue, log, and undo.

Concept

An action you can hold in your hand

🍴 Real-world analogy

A Command is a restaurant order ticket. The waiter (the client) writes your request onto a slip — “table 4: steak, medium” — and that slip fully captures what to do. The waiter hangs it on the rail (a queue); the ticket can wait, be re-fired if the plate is dropped, or be voided (undone) if you change your mind. The kitchen (the receiver) reads the slip and cooks, without knowing which waiter wrote it or when it was written. The expo who calls the tickets (the invoker) triggers the work but never touches a pan. That separation — a written request, a queue, a receiver that acts on demand — is exactly the Command pattern.

Normally a method call vanishes the instant it runs. Wrap it in a Command object — with an execute() (and often undo()) — and the action becomes data you can keep. An invoker (a button, a queue, a scheduler) runs commands without knowing what they do.

Command powers undo/redo, task queues, macro recording, and GUI buttons/menu items that trigger the same action. Because a command captures everything it needs, you can run it now, later, on another thread, or replay a whole history.

    


    
Intent: decouple the invoker from the receiver

    
The point of Command is to encapsulate a request as an object. The thing that triggers the work (a button, a menu, a scheduler — the invoker) is separated from the thing that does the work (the receiver). The invoker holds a Command reference and calls execute(); it neither knows nor cares what happens inside. That indirection is what lets you parameterize objects with an action, queue it, log it, or reverse it.




    
The four participants

    
Every Command setup has the same cast. The Command interface declares execute(). A Concrete Command implements it and holds a reference to a Receiver plus any parameters the call needs. The Invoker stores and triggers commands. The Client wires a concrete command to its receiver and hands it to the invoker.




    
A worked example: a remote control

    
The classic Command example is a programmable remote: each slot holds a command object, so the remote (invoker) is generic and every device (receiver) plugs in without the remote knowing its API. Adding a new gadget means writing a new concrete command, not editing the remote.




    
Undo/redo: the big payoff of reifying actions

    
Because a command is an object, it can remember how to reverse itself. Add an undo() method and keep a history stack: push each command as you execute it, pop and undo() for Ctrl+Z, and keep a second “redo” stack for Ctrl+Y. The command must capture whatever state undo needs — the old value, the deleted text, the previous position.




    
Queuing, logging, scheduling

    
A reified action is just data, so you can put it anywhere data goes. Drop commands on a task queue for a worker thread; batch several into a macro command that runs them in order; log each executed command to disk so that after a crash you can replay the log to rebuild state (the transactional / event-sourcing idea). None of this is possible with a bare method call, which leaves nothing behind.




    
The modern Java form: a command is often just a lambda

    
Command's original ceremony — an interface plus a class per action — largely dissolves in modern Java. A no-undo command is just a functional interface, so Runnable is a command and a lambda IS a concrete command. And ExecutorService.submit(Runnable) is literally the pattern: the runnable is the command, the executor is the invoker that decides when and on which thread it runs. Reach for an explicit interface only when you need undo() or extra metadata.




    
Command vs Strategy

    
Both wrap behavior in an object, so they look alike. The difference is intent. A Strategy is an interchangeable algorithm — a different how for one well-defined job (e.g. which sort or which compression). A Command is a whole request or action — a what to do, frequently bound to a specific receiver and often carrying undo(). You swap a strategy to change the way a task is done; you queue, log, and replay commands because each one is a task.

Coming from another language

    
What will surprise you

      
Coming from Python
A callable (or functools.partial) captures an action and its arguments — a lightweight command. For undo you still store paired do/undo callables, which is the same idea with less ceremony.

      
Coming from JavaScript
Functions and closures are commands you can push onto an undo stack. Redux actions are command-like objects describing “what happened,” enabling logging and time-travel debugging.

      
Coming from C#
WPF/MVVM has a first-class ICommand interface for buttons and menus — the pattern is built into the UI framework. Action delegates serve as lightweight commands too.

  






  

    
Exercises

    
Make it stick

      
1 · What enables undo?
Why can a Command implement undo() when a plain method call can’t be “taken back”?
💡 Show hint
The command object captures the state/inputs needed to reverse itself (e.g. what text it inserted and where). A bare call leaves nothing behind to reverse; the object persists that information.

      
2 · One action, two buttons
A toolbar button and a menu item should both “Save.” How does Command avoid duplicating logic?
💡 Show hint
Both invokers hold the same SaveCommand object and call execute(). The action lives in one place; the button and menu are just different invokers triggering it.

      
3 · Name the four participants
In new Button(new LightOnCommand(light)), which object is the invoker, which is the concrete command, and which is the receiver?
💡 Show hint
Button is the invoker (it triggers execute()), LightOnCommand is the concrete command, and light is the receiver that holds the real on() logic. The code that wires them together is the client.

      
4 · Undo a macro
A MacroCommand runs steps A, B, C in order. In what order must its undo() reverse them, and why?
💡 Show hint
C, then B, then A — reverse order. Later steps may depend on the state left by earlier ones, so you must unwind the most recent change first, exactly like popping an undo stack.

      
5 · Command or Strategy?
You have an object that picks which compression algorithm a backup uses. Is that a Command or a Strategy? What if instead it represented “run this backup now, and be able to roll it back”?
💡 Show hint
Choosing the algorithm is a Strategy — an interchangeable how for one job. “Run this backup, with rollback” is a Command — a whole self-contained request (a what) you can queue, log, and undo().
