Eight primitives and their object twins

Java has two parallel number worlds: lightweight primitives (int, long, double…) and their boxed objects (Integer, Long, Double). Autoboxing blurs the line — until a cached == comparison or a surprise NullPointerException reminds you the line is real.

Concept

Primitives are values; wrappers are objects

🏷 Real-world analogy

A primitive is cash in your pocket; a reference is a claim ticket. An int is like a €42 note — the value itself, right there in your hand (on the stack). A reference type is a coat-check ticket: the variable holds only a small stub that points to the real object sitting in the warehouse (the heap); copy the ticket and both stubs still redeem the same coat. Autoboxing is sealing that cash inside a labeled envelope stamped “Integer” so it can be filed alongside the objects — and the clerk keeps a rack of pre-printed envelopes for small amounts (−128..127), handing back the identical envelope each time, which is exactly why == on two small boxed values surprisingly matches.

An int is 32 raw bits on the stack. An Integer is a heap object that wraps an int. Autoboxing converts between them automatically, so you rarely notice — but the conversion is real and occasionally bites.

The JVM caches boxed integers from −128 to 127, so == on small values accidentally works and on large ones doesn't. The rule: compare objects with .equals(), reserve == for primitives and identity.

    


    
The eight primitives (and what they cost)

    
Java has exactly eight built-in primitive types — you cannot define more. Each has a fixed size and range that never varies across platforms, which is what makes Java's integer math portable. Everything else in the language is a reference type.

    


    
What a variable actually holds

    
This is the mental model that unlocks Java. A primitive variable holds the value itself. A reference variable holds a reference (think: a managed pointer) to an object on the heap — never the object. Assignment and argument passing copy what the variable holds: the value for primitives, the reference for objects. Java is always pass-by-value; for objects, it is the reference that is passed by value.

    


    
Autoboxing, unboxing & the null trap

    
The compiler silently converts between a primitive and its wrapper: int ↔ Integer, double ↔ Double, and so on. Convenient — but unboxing a null wrapper calls a method on null and throws NullPointerException at a line that looks like harmless arithmetic. Wrappers can be null; primitives can never be.

    


    
Why == on boxed values is a bug

    
For wrapper objects, == compares identity (same object?), not value. Autoboxing routes through Integer.valueOf, which caches instances for −128 to 127 and returns fresh objects outside that range. So the same code gives different answers depending on the magnitude — a classic heisenbug. Always compare wrapper values with .equals().

    


    
Widening, narrowing & silent overflow

    
Java widens smaller types to larger ones automatically (int → long → double) because no information is lost. Going the other way — narrowing — can lose data, so it demands an explicit cast. The cast never throws: it just truncates or wraps, so overflow is completely silent. This is a frequent source of subtle numeric bugs.

    


    
var: inferred type, still static

    
Since Java 10, var lets the compiler infer a local variable's type from its initializer. It is pure convenience — the variable is still statically, permanently typed; var is not a dynamic type and not an Object. It works only for local variables with an initializer: not fields, not method parameters, not null alone.

    


    
Numeric literals & default values

    
Literals carry a type of their own. An integer literal is an int unless suffixed with L; a decimal literal is a double unless suffixed with f. Underscores group digits for readability, and prefixes give hex/binary forms. Separately, fields (not local variables) get well-defined default values automatically; local variables must be assigned before use or the compiler complains.

Coming from another language

    
What will surprise you

      
Coming from Python
Python 3's / always gives a float and ints are arbitrary precision. Java's int is fixed 32-bit and / truncates; use //-style thinking and reach for long or BigInteger when values grow.

      
Coming from JavaScript
JS has one number type (double). Java's eight primitives mean you choose int vs long vs double deliberately, and integer math is exact — no 0.1 + 0.2 surprises for whole numbers.

      
Coming from C#
Almost the same model: C# value types vs reference types, with boxing on assignment to object. C# lacks Java's small-integer cache, so the == gotcha is Java-specific.

  






  

    
Exercises

    
Make it stick

      
1 · Two ways to be 1000
Integer x = 1000, y = 1000; Does x == y return true? What about x.equals(y)?
💡 Show hint
x == y is false (1000 is outside the −128..127 cache, so they're distinct objects). x.equals(y) is true. Always use .equals for value comparison.

      
2 · The hidden NPE
Integer count = null; int n = count; compiles fine. What happens at runtime?
💡 Show hint
It throws NullPointerException on the unboxing line: assigning a null Integer to an int calls count.intValue() on null.

      
3 · The overflow that isn't an error
You compute int total = 2_000_000_000 + 2_000_000_000; and get a negative number. Why, and how do you fix it?
💡 Show hint
Both operands are int, so the addition is done in 32-bit int arithmetic and overflows silently (wrapping past Integer.MAX_VALUE) — no exception. Widen at least one operand before the add so the whole computation happens in 64-bit: long total = 2_000_000_000L + 2_000_000_000;.

      
4 · Copy the value or the reference?
After int[] a = {1,2,3}; int[] b = a; b[0] = 9; what is a[0]? Contrast with int x = 1; int y = x; y = 9; — what is x?
💡 Show hint
a[0] is 9: b = a copies the reference, so both name the same array on the heap. But x stays 1: primitives copy the value, so y is independent. That difference is the whole primitive-vs-reference distinction.

      
5 · What can var infer?
Which of these compile? var a = 5;   var b;   var c = null;   var d = new ArrayList<String>();
💡 Show hint
a (inferred int) and d (inferred ArrayList<String>) compile. b fails — var needs an initializer to infer from. c fails — the type of null is unknown. var is compile-time inference only; the type is fixed once inferred.
