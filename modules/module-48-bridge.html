Let two things vary independently

Real-world picture: a TV remote. The same remote design works with a TV, a soundbar, or a projector, and you can upgrade the remote (basic → smart) without changing the devices. Bridge splits an abstraction from its implementation so each can evolve on its own.

Concept

Hold the implementation, don’t inherit it

🏷 Real-world analogy

Bridge is a TV remote and the TV it points at. The remote (the abstraction) and the device (the implementation) evolve on their own: any remote works any brand of TV because they meet at a tiny agreed interface — power, volume, channel. Ship a fancier remote (add a voice button) and every existing TV still works; a manufacturer ships a new TV and every existing remote still drives it. Nobody builds a separate remote model per TV brand — that grid of combinations is exactly the class explosion Bridge dissolves. The remote simply holds a reference to whatever device it is paired with and delegates the low-level work across the bridge.

Suppose you have 2 kinds of remote and 3 devices. Subclassing every combination gives 6 classes — and 12 if a device is added. Bridge instead has the abstraction (Remote) hold a reference to the implementation (Device). Now you add classes; you don’t multiply them.

Bridge is “prefer composition over inheritance” (module 10) applied to two dimensions of change. Recognize it when you’d otherwise get a class explosion from combining two independent hierarchies — like shapes × renderers, or messages × delivery channels.

    

    
    
Intent: decouple an abstraction from its implementation

    
The Gang of Four one-liner is “decouple an abstraction from its implementation so the two can vary independently.” The trick is that both are their own class hierarchy. The abstraction (what callers use — Shape, Remote) is joined to the implementor (the low-level engine — Renderer, Device) by a reference, not by extends. It is composition, not inheritance, taken to two dimensions.

    

    
The class explosion it prevents: M×N → M+N

    
When two features vary at once and you model every pairing with a subclass, the class count is the product of the axes. Bridge makes it the sum. That is the whole payoff: growth becomes linear instead of combinatorial, and adding one shape or one renderer touches exactly one class.

    

    
Anatomy of the bridge

    
The abstraction keeps a field of the implementor interface and delegates each high-level operation down to it. Subclasses of the abstraction are called refined abstractions; they add or reshape high-level behaviour and never mention a concrete implementor. Concrete implementors provide the primitives — and can be swapped at construction time or even at runtime.

    

    
A worked example: RemoteControl → Device

    
Here the two hierarchies are complete. Remote is the abstraction and Device the implementor; SmartRemote is a refined abstraction that adds mute() for free across every device. Construct any remote with any device and the bridge routes each call to the right implementation.

    

    
Bridge vs Adapter

    
Both put one object in front of another, so they are easy to confuse. The difference is intent and timing. Adapter is a retrofit: an incompatible class already exists and you wrap it to fit an interface. Bridge is a deliberate up-front split of two dimensions you know will both change. Adapter reacts to the past; Bridge plans for the future.

    

    
Bridge vs Strategy

    
Structurally they look the same — an object holds a reference to swappable behaviour. But Strategy is behavioural: it varies a single algorithm behind one method. Bridge is structural: it separates an entire abstraction hierarchy from an entire implementation hierarchy, both of which keep growing. Strategy varies one plug-in point; Bridge organises two whole family trees.

Coming from another language

    
What will surprise you

      
Coming from Python
Duck typing makes the implementation just “any object with these methods,” which you pass into the abstraction. The class explosion never threatens you the way it does in strict-inheritance languages.

      
Coming from JavaScript
Composition by passing an implementation object is the everyday approach; Bridge is just naming that discipline when two hierarchies would otherwise multiply.

      
Coming from Go
Go has no inheritance, so Bridge is the default: a struct holds an interface value. Combining two axes is always composition, never a subclass grid.

  






  

    
Exercises

    
Make it stick

      
1 · Bridge vs Adapter
Both involve one object holding another. How does Bridge differ in intent from Adapter (37)?
💡 Show hint
Adapter makes an existing, incompatible class fit an interface after the fact. Bridge is a deliberate up-front design that separates an abstraction from its implementation so both can vary independently. Adapter = retrofit; Bridge = planned.

      
2 · Spot the explosion
You’re about to write SmsUrgentMessage, SmsNormalMessage, EmailUrgentMessage… Why is Bridge the fix?
💡 Show hint
Two independent axes (message type × delivery channel) are being multiplied into subclasses. Bridge holds a Channel reference inside Message, so you add a few classes per axis instead of one per combination.

      
3 · Bridge vs Strategy
Both hold a reference to swappable behaviour. So what actually makes Bridge different from Strategy (41)?
💡 Show hint
Strategy is behavioural — it swaps one algorithm behind a single method. Bridge is structural — it separates a whole abstraction hierarchy (Shape, Circle…) from a whole implementation hierarchy (Renderer, Svg…), each of which keeps growing on its own axis.

      
4 · Count the classes
You need to render 4 shapes on 3 different back-ends. How many classes with subclass-per-combination, and how many with Bridge?
💡 Show hint
Subclass grid: 4 × 3 = 12 combination classes. Bridge: 4 + 3 = 7 classes (4 shapes on one axis, 3 renderers on the other). And each new shape or renderer then adds exactly one class instead of a whole row or column.

      
5 · Which side is which?
In new AdvancedRemote(new Projector()), which object is the abstraction and which is the implementor — and where does a high-level skipToNext() belong versus a low-level setInputSource()?
💡 Show hint
The Remote hierarchy is the abstraction (high-level operations the user invokes); Device/Projector is the implementor (the primitives). skipToNext() is a refined-abstraction method on AdvancedRemote built out of primitives; setInputSource() is a primitive on the Device side. Adding skipToNext() touches no device class at all.
