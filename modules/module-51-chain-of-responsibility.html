Pass it along until someone handles it

Real-world picture: calling tech support. Tier 1 tries to help; if they can’t, they escalate to tier 2; if they can’t, it goes to a manager. Each level either handles your request or passes it on. Chain of Responsibility sends a request along a line of handlers until one deals with it.

Concept

A line of handlers, each with a choice

🏷 Real-world analogy

Chain of Responsibility is a customer-support escalation ladder. You open a ticket and it lands with tier 1. If they can resolve it, you’re done; if not, they escalate it to tier 2, and from there to a manager. You, the customer, never choose who fixes your problem — you hand it to the front of the line, and each rung decides for itself whether to handle the ticket or pass it up. Slot in a new tier, or reorder the rungs, and the person filing the ticket changes nothing. And if it climbs past the top rung with nobody able to help, it simply falls off the end — unresolved, unless someone parked a catch-all at the top.

Instead of one big method with a tangle of if/else deciding who handles what, you make a chain of small handler objects. Each handler either processes the request or forwards it to the next. The sender doesn’t know (or care) which handler will deal with it.

This decouples senders from receivers and lets you reorder or insert handlers freely. It’s the backbone of request pipelines: servlet Filter chains, logging handlers, and validation pipelines all work this way (it’s the same idea as web “middleware”).

    

    
    
Intent: decouple the sender from the receiver

    
The pattern’s goal is to give more than one object a chance to handle a request without the sender knowing which one will. You avoid coupling the caller to a specific receiver by threading the request through a chain of candidate handlers; the first one able to deal with it does, and the rest are spared. The sender only ever touches the head of the chain.

    

    
The handler’s two jobs: check, then process or forward

    
Structurally, a handler is just an object with a reference to the next handler and a handle() method. That method asks one question — can I deal with this? — and either processes the request or delegates to next. Because the wiring is a plain linked list, you compose chains at runtime and insert, remove, or reorder links without editing any handler.

    

    
A worked example: a purchase-approval chain

    
Approval limits are the textbook case. A team lead signs off small amounts, a manager larger ones, a director larger still. Wire them into a chain once, then throw amounts at the head; each request travels only as far as it must. Note the last else — a request too big for everyone falls off the end.

    

    
Handle-or-forward, and the request that falls off the end

    
Each link makes an independent handle-vs-forward decision, so a request may be consumed early, consumed late, or never consumed at all. Falling off the end unhandled is a legitimate design choice, not a bug — but decide deliberately: throw, log, or park a catch-all default handler at the tail so nothing vanishes silently.

    

    
You already use this: filters, security, logging

    
Chain of Responsibility is everywhere in the Java ecosystem. Servlet Filter chains, the Spring Security filter chain, java.util.logging handler/parent-logger propagation, and even exception propagation up the call stack are all the same idea — the request keeps moving until something takes responsibility. Web “middleware” pipelines are this pattern by another name.

    

    
Chain of Responsibility vs Decorator

    
Both build a linked stack of wrappers, which makes them easy to confuse. The difference is intent: a decorator has every layer add behaviour and then always call the layer it wraps, so all of them contribute. A chain gives one handler the chance to stop the request — once handled, the remaining links never run. Additive pipeline versus first-willing-handler.

Coming from another language

    
What will surprise you

      
Coming from Python
A list of handler callables you try in order, or WSGI middleware wrapping an app. Logging’s handler hierarchy (record propagates up to parent loggers) is chain-of-responsibility in the stdlib.

      
Coming from JavaScript
This is Express/Koa middleware — each function gets next() and either responds or passes control along. You use the pattern every time you write a middleware stack.

      
Coming from C#
ASP.NET Core’s middleware pipeline and DelegatingHandler chains for HttpClient are exactly this — each link handles or calls the next.

  






  

    
Exercises

    
Make it stick

      
1 · Why not one big if/else?
What does a handler chain give you that a single method full of if/else branches doesn’t?
💡 Show hint
You can add, remove, and reorder handlers independently without touching a giant method, and senders stay decoupled from who handles the request. Each handler is small and testable on its own (also better for Open/Closed).

      
2 · Unhandled requests
What happens if a request reaches the end of the chain and no handler accepted it? How might you design for that?
💡 Show hint
By default it’s silently dropped. Add a default/fallback handler at the end that always handles (logs an error, returns a 404, etc.) so nothing falls through unnoticed.

      
3 · Build an approval chain
Wire a TeamLead (≤$1,000), Manager (≤$10,000), and Director (≤$100,000) into a chain. Which handler prints for a $7,500 request, and which for $250,000?
💡 Show hint
$7,500 escalates past the team lead and is approved by the Manager. $250,000 exceeds every limit, reaches the tail with no successor, and hits the final else — “No one can approve”. That’s a request falling off the end.

      
4 · CoR or Decorator?
You’re wrapping an input stream so each layer buffers, then decompresses, then decrypts the bytes — all of them always run. Is that Chain of Responsibility or Decorator? Why?
💡 Show hint
Decorator. Every layer contributes and then delegates to the one it wraps — nobody “stops” the request. Chain of Responsibility is for when you want the first willing handler to take it and the rest to be skipped.

      
5 · Spot the pattern in the JDK
A servlet Filter calls chain.doFilter(req, res) to continue, or writes a 401 and returns without calling it. Which two Chain-of-Responsibility decisions do those branches correspond to?
💡 Show hint
Calling chain.doFilter is forward (delegate to the next link); writing the 401 and returning is handle (this link takes responsibility and stops the chain). Same intent as exception propagation: bubble up, or catch it here.
