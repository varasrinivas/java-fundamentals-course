Immutable text and the string pool

Strings are objects, they're immutable, and identical literals are shared in a pool. That trio explains why == on strings is a trap, why heavy concatenation wants a StringBuilder, and why text blocks were such a welcome addition.

Concept

Immutable, pooled, and built efficiently

🏷 Real-world analogy

A String is an engraved stone tablet. Once a mason has carved the letters, the stone is fixed — there is no eraser. Any “edit” really means chiselling a brand-new tablet and leaving the old one untouched; that is immutability. The string pool is a shared library at the front of the workshop: for common phrases the JVM keeps one master tablet and hands out the same stone to everyone who asks, so it never re-carves a duplicate — which is why two identical literals are literally the same object. When you deliberately order a fresh copy (new String("hi")) you get a private tablet that reads the same but sits at a different address. And a StringBuilder is the whiteboard beside the workbench: you scribble, wipe, and rearrange as much as you like, then carve the final stone once when the text is settled.

A String never changes — every “modification” returns a new object. String literals are interned in a shared pool, so two identical literals are the same reference; a new String("x") is not. Hence: compare text with .equals(), never ==.

Because each + on strings allocates, looping concatenation should use a StringBuilder. For multi-line text, text blocks ("""...""") keep JSON/SQL readable without escaping.

    


    
Immutability — and why the language leans on it

    
A String's backing array is private final and never mutated after construction. That single guarantee buys a lot: strings can be shared freely across threads with no locking, they make safe Map keys because their hashCode can be computed once and cached, and they can be used as security-sensitive tokens (class names, file paths) that a caller can't rewrite behind your back. The catch: methods that look mutating actually return a new object — ignore the result and nothing changes.



    
The string pool & interning: == vs .equals()

    
Every string literal lives in the string pool (a table of unique, interned instances). The compiler also folds constant expressions: "a" + "b" is computed at compile time and interned, so it equals the literal "ab" by reference. But a value built at runtime, or made with new String, is a distinct heap object. Since == compares references, it gives you inconsistent answers on text — always use .equals(). You can force a runtime value into the pool with .intern().



    
Building strings: why + in a loop is O(n²)

    
A single a + b + c on one line is fine — the compiler fuses it into one efficient build step. The trap is += inside a loop: because strings are immutable, each iteration copies the entire accumulated text into a new object, so n appends do roughly n²/2 character copies. A StringBuilder keeps one growing buffer and appends in place — linear time. Use StringBuffer only when the buffer is genuinely shared across threads; its synchronization is pure overhead otherwise.



    
Text blocks for multi-line text (Java 15+)

    
A text block opens and closes with three double-quotes and spans multiple lines with no \n or + clutter — ideal for JSON, SQL, or HTML. The content starts on the line after the opening delimiter, and the compiler strips incidental indentation measured from the least-indented line (usually the closing """), so you can indent the block to match your code without polluting the value. It is still an ordinary, immutable String at runtime.



    
char vs Unicode code points

    
A Java char is a 16-bit UTF-16 code unit, not a full character. Characters in the Basic Multilingual Plane fit in one char, but anything above it — emoji, many CJK extensions — is stored as a surrogate pair of two chars. So length() counts code units, not visible characters, and indexing into an emoji gives you half of it. When you need real characters, iterate codePoints() rather than chars().



    
Formatting, joining, splitting, stripping

    
Beyond concatenation, the everyday toolkit: String.format (or the instance formatted method) for printf-style templates, String.join to glue pieces with a delimiter, split to break on a regex, and trimming. Prefer strip() over the legacy trim(): trim only removes ASCII control chars (≤ U+0020), while Unicode-aware strip also handles non-breaking spaces and other Unicode whitespace.

Coming from another language

    
What will surprise you

      
Coming from Python
Good news: Python strings are also immutable and small ones are interned, so the mental model carries over. The Java twist is the explicit ==-vs-.equals() distinction — in Python == already compares text.

      
Coming from JavaScript
JS strings are immutable primitives and === compares by value, so JS hides the pool. In Java a String is an object, so == compares references — use .equals() or you'll get intermittent false negatives.

      
Coming from C#
Nearly identical: C# strings are immutable, interned, and you compare with == (overloaded) or .Equals. Java's StringBuilder ≈ C#'s, and Java text blocks ≈ C# raw/verbatim strings.

  






  

    
Exercises

    
Make it stick

      
1 · The == bug
String x = new String("hi");  Why might x == "hi" be false while x.equals("hi") is true?
💡 Show hint
new String forces a fresh object outside the pool, so == (reference identity) is false. .equals compares the characters, which match — so it's true. Always compare text with .equals.

      
2 · Why StringBuilder?
Concatenating 10,000 strings in a loop with += is slow. What's happening, and the fix?
💡 Show hint
Each += allocates a new String and copies everything so far — O(n²) work and garbage. Use a StringBuilder (one growing buffer, append in place) and call toString() once at the end.

      
3 · Pool or not?
Given String a = "ab"; String b = "a" + "b"; String c = new String("ab"); — which of a==b and a==c are true?
💡 Show hint
a==b is true: "a" + "b" is a compile-time constant, so it is folded to "ab" and interned to the same pooled object as a. a==c is false: new String always allocates a fresh heap object. Both are .equals()-true.

      
4 · Counting an emoji
Why does "\uD83D\uDE00".length() return 2 when it displays as a single emoji? How do you count the real characters?
💡 Show hint
A char is a 16-bit UTF-16 code unit. The emoji sits above the Basic Multilingual Plane, so it is stored as a surrogate pair — two chars — and length() counts code units. Use codePointCount(0, length()) or codePoints().count() to count actual characters.

      
5 · strip vs trim
A field arrives with a leading non-breaking space (\u00A0) and trim() doesn't remove it. Why, and what should you call instead?
💡 Show hint
trim() only strips characters with code ≤ U+0020 (ASCII control/space), and U+00A0 is above that. strip() (Java 11+) is Unicode-aware and removes it. Prefer strip() in new code; also see stripLeading() / stripTrailing().
