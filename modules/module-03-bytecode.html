What javac actually produces

javac doesn’t make machine code — it makes bytecode for a stack machine that adds by pushing operands and popping results. Peek inside a .class file once and the JVM stops being a black box.

Concept

A stack machine, not a register machine

🍳 Real-world analogy

Compiling Java is like a chef writing a recipe that any kitchen on earth can cook. Your .java source is the recipe written in the chef’s native language — expressive, readable, full of shorthand only humans follow. javac is the translator: it doesn’t cook anything, it rewrites the recipe into a set of small, unambiguous picture-instructions — that is the bytecode in the .class file. Those picture-cards are deliberately dumb and standardized (“put ingredient on counter,” “combine top two items”), so any kitchen — a Windows kitchen, a Linux kitchen, an ARM phone kitchen — can follow them. The JVM is the line cook: it reads the cards one at a time and works on a single prep counter (the operand stack), setting items down and combining them. Before starting, a health inspector (the bytecode verifier) checks the cards make sense — you never combine two items when only one is on the counter. Ship the cards, not the chef’s prose, and every kitchen produces the same dish.

Your CPU has registers; the JVM has an operand stack. To compute 2 + 3, bytecode pushes 2, pushes 3, then iadd pops both and pushes 5. Every method is a little stack program.

Compilation is a pipeline: source text → tokens (lexing) → an AST (parsing + type checking) → bytecode plus a constant pool of names and literals. You can read any of it with javap -c YourClass.

    


    
What javac actually does: .java → .class

    
javac is not a machine-code compiler. It reads one or more .java files, type-checks them, and writes one .class file per class (including a separate file for each nested and anonymous class, named like Outer$1.class). No linking step, no executable — each class is compiled independently against the types it can see on the classpath.



    
Anatomy of a .class file & the constant pool

    
Every .class file starts with the 4-byte magic number 0xCAFEBABE, then version numbers, then the constant pool — a table of every string literal, class name, method name, and type descriptor the class refers to. Bytecode never embeds a name inline; it refers to pool entries by index. Deduplicating symbols this way keeps class files compact and makes them easy to link at load time.

The execution model is a stack, not registers

    
A physical CPU names registers (rax, r1…) and encodes them into each instruction. The JVM instead gives every method frame an operand stack plus a numbered array of local variables. Instructions push operands, and arithmetic opcodes pop their inputs and push the result — so they need no register operands at all, which is exactly why the same bytecode runs on any CPU.

How source constructs map to opcodes

    
There is a fairly direct mapping from what you type to the opcodes emitted. Arithmetic becomes typed opcodes (iadd, ladd, dadd — the leading letter is the type). Method calls pick one of four invoke opcodes depending on how the target is resolved. Object creation is a two-step new then invokespecial for the constructor.



    
invokedynamic is the interesting one: it defers deciding what to call until the first execution, handing control to a bootstrap method. Java uses it to implement lambdas (via LambdaMetafactory) and modern string concatenation without baking the strategy into the class file.

    
Why the JVM verifies bytecode

    
Because .class files can come from anywhere — a network, a code generator, a hand-edited hex dump — the JVM cannot trust that they were produced by an honest javac. Before a class runs, the bytecode verifier statically proves the code is safe: the operand stack never underflows or overflows, every local is written before it is read, types line up (no treating an int as a reference), and every branch lands on a valid instruction. This is what lets the interpreter and JIT skip runtime bounds/type checks that a naive stack machine would need.



    
Why bytecode exists at all

    
Two payoffs justify the extra layer. First, portability: “compile once, run anywhere” works because the .class targets the abstract JVM, and each platform ships its own JVM that turns bytecode into native code at runtime (the JIT). Second, bytecode is a shared target: Kotlin, Scala, Groovy, and Clojure all compile to the very same .class format, so they interoperate and reuse the entire JVM ecosystem — the GC, the JIT, every Java library — for free.

Coming from another language

    
What will surprise you

      
Coming from Python
CPython also compiles to bytecode for a stack machine (see dis.dis). The big difference: Java ships and verifies its .class bytecode and JIT-compiles it to native; CPython mostly interprets .pyc.

      
Coming from JavaScript
There's no user-visible bytecode file in JS — V8 builds bytecode internally and throws it away. Java makes the artifact explicit, which is why tools like javap, ASM, and bytecode agents exist.

      
Coming from Go
Go skips the VM entirely and emits native machine code. You can read Go's assembly with go tool objdump, but it targets a real CPU — Java bytecode targets the imaginary one.

  






  

    
Exercises

    
Make it stick

      
1 · Predict the order
For 5 - 2 - 1, write the sequence of pushes and isubs. Does it evaluate left-to-right or right-to-left?
💡 Show hint
Left-to-right: push 5, push 2, isub → 3; push 1, isub → 2. Subtraction is left-associative, so it is (5-2)-1, not 5-(2-1).

      
2 · Why a constant pool?
A class uses the string "OK" in five places. How many times is it stored in the .class file?
💡 Show hint
Once. The constant pool deduplicates literals and symbolic names; the five usages all reference the same pool index, keeping the file compact.

      
3 · Which invoke opcode?
For each call, name the invoke opcode javac emits: (a) Math.abs(x), (b) account.deposit(10) on a class, (c) list.add(x) where list is declared List.
💡 Show hint
(a) invokestatic — abs is static, no receiver. (b) invokevirtual — a normal instance method resolved on the runtime type. (c) invokeinterface — the declared type List is an interface, so dispatch goes through the interface table.

      
4 · What flag shows the bytecode?
You have Calc.class and want to see the actual opcodes for its add method, plus the constant pool. Which two javap invocations do you run?
💡 Show hint
javap -c Calc disassembles the method bodies into opcodes; javap -v Calc (verbose) additionally dumps the header, flags, and the full constant pool. Plain javap Calc shows only the public signatures.

      
5 · Trust nothing
A class file is generated at runtime by a library (not by javac) and its bytecode leaves the operand stack unbalanced. When and how does the JVM catch this, and what error do you get?
💡 Show hint
At class load / link time, before the method ever runs, the bytecode verifier statically checks stack balance and types. An unbalanced stack throws java.lang.VerifyError. This is why the JVM can safely run .class files from untrusted sources — it never assumes javac produced them.
