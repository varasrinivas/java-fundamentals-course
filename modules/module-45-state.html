Behavior that changes with the mode

Real-world picture: a traffic light. Green lets you go, yellow says slow down, red stops you — the same light behaves completely differently depending on its current state, and it follows fixed transitions. The State pattern lets an object change its behavior when its internal state changes, as if it changed class.

Concept

Each state is its own object

🚦 Real-world analogy

The State pattern is a traffic light. Feed the very same “tick” event into the light and it does something different depending on which lamp is currently lit: a tick on green turns it yellow, a tick on yellow turns it red, a tick on red turns it back to green. The light’s behavior is driven entirely by its internal state, and each state already knows which state comes next — there is no giant “if the light is currently…” conditional bolted onto the wiring. Swap the pattern in and each colored lamp becomes its own small object that owns both its behavior and its transition.

The naive version is a giant switch(status) repeated in every method — brittle and sprawling. The State pattern makes each state a class implementing a shared interface; the context delegates behavior to its current state object, and states decide the transitions.

State turns tangled conditionals into small, focused classes and makes the legal transitions explicit. You’ll meet it in workflow engines (draft → review → published), vending machines, TCP connection states, and game character modes.

    
The pattern’s intent

    
The Gang of Four define State as: “allow an object to alter its behavior when its internal state changes — the object will appear to change its class.” That last phrase is the whole idea. From the caller’s side, player.play() does one thing while stopped and a completely different thing while paused, as though the reference suddenly pointed at a different type. Internally there’s one context object holding a reference to a state object, and every public method just forwards to it.

    

    
Because the context delegates, you can add a whole new behavior mode by writing one class — the context never changes.

    
Replacing the giant switch

    
The tell-tale smell State fixes is the same switch(status) duplicated across every method. Each state class instead pulls together all the behavior for one mode in one place. Here is a media player with Stopped, Playing, and Paused states, each implementing the same interface and each deciding its own transitions.

    

    
Notice how illegal events (pausing while stopped) become a quiet no-op inside the state that knows it’s illegal, instead of a defensive if scattered everywhere.

    
Who triggers the transition?

    
There are two schools. In the classic form, each state decides the next state and calls context.setState(…) — transitions live next to the behavior that causes them. Alternatively the context owns a transition table and the states stay purely behavioral. Table-driven transitions are easier to visualize and validate as a whole; state-driven transitions keep related logic together.

    

    
An enum as a compact state machine

    
Java enums can carry constant-specific method bodies: declare an abstract method on the enum and let each constant override it. That gives you a state machine with zero boilerplate classes — the constants are the states, and because enum constants are singletons, transitions allocate nothing.

    

    
This is the most idiomatic Java form when the states are fixed and known at compile time. Reach for full classes only when a state needs its own fields or must be created dynamically.

    
State vs Strategy

    
State and Strategy share an identical UML diagram — an interface plus a field the context delegates to — so they’re constantly confused. The difference is entirely in intent. Strategy is about interchangeable algorithms the client chooses (and usually leaves put); State is about a self-driven lifecycle where the object swaps its own behavior as events arrive.

    

    
Pitfalls: shared data & transition explosion

    
Two traps show up in real code. First, where does shared data live? Keep it in the context and pass the context into each state method — don’t copy it into every state object. Second, transition explosion: with N states and M events you can drift toward N×M methods. Keep states stateless singletons, give a base class no-op defaults, and consider a transition table once the graph gets busy.

Coming from another language

    
What will surprise you

      
Coming from Python
Often done by swapping a state object, or with a dict mapping state → handler function. Enums plus a transition table are a common lightweight version; the OO State pattern is the same idea as classes.

      
Coming from JavaScript
Finite-state-machine libraries (e.g. XState) formalize this, but a plain object whose methods are swapped per state captures it. Replaces the dreaded switch(status) sprawl just like in Java.

      
Coming from C#
Identical pattern — a state interface with one class per state and a context that delegates. Workflow and game frameworks in .NET use it heavily, same as Java’s workflow engines.

  






  

    
Exercises

    
Make it stick

      
1 · What smell does it fix?
You see the same switch(status) copy-pasted across five methods. Why is State a good remedy?
💡 Show hint
That duplicated conditional is the smell. State moves each branch into its own class, so behavior for a status lives in one place and the methods just delegate. Adding a status becomes adding a class, not editing five switches.

      
2 · State vs Strategy
State and Strategy have the same class diagram. What’s the key difference in how the object changes?
💡 Show hint
In Strategy, the client picks the algorithm and it usually stays put. In State, the object transitions itself between states over time (often the states decide the next state), changing its own behavior as it runs.

      
3 · Where does the data live?
A document workflow has Draft, Review, and Published states, and every state needs the document’s text. Where should that text be stored, and how do the states reach it?
💡 Show hint
Store shared data in the context (the Doc), not duplicated inside each state. Pass the context into each state method — state.publish(this) — so the state can read and mutate it. State objects then stay stateless and can be shared singletons.

      
4 · Enum or classes?
When is the enum form (constants with an abstract next()) the better choice, and when do you need full state classes?
💡 Show hint
Use the enum when the set of states is fixed and known at compile time and the states hold no per-instance data — you get singletons and zero boilerplate. Reach for full classes when a state needs its own fields, must be created dynamically, or the state set is open for extension.

      
5 · Trace the transitions
Starting from Stopped, what states does the media player pass through for the sequence play(), pause(), play(), stop()? Who performs each transition?
💡 Show hint
Stopped → Playing (play) → Paused (pause) → Playing (play resumes) → Stopped (stop). Each current state performs its own transition by calling p.setState(…); the context never decides — it only delegates.
