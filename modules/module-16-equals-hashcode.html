Why == lies, and equals tells the truth

Two objects can hold identical data yet be different instances. equals() defines value-equality; hashCode() must agree with it. Break their contract and HashMap silently loses your keys — one of Java's most common subtle bugs.

Concept

Identity vs value, and the rule that ties them together

📚 Real-world analogy

equals and hashCode are a library catalog. Two physical copies of the same title are “the same book” because they share an ISBN — that is logical equality (what equals tests), not “the same physical object” (what == tests). The shelf number is the hashCode: a quick label telling the librarian which shelf to walk to before scanning the few books there. The rule that makes the catalog work: equal books must get the same shelf number. If you re-shelved an identical copy under a different number (equal objects, different hash), a patron following the catalog would walk to the wrong shelf and swear the book isn’t in the library — even though it is. That is exactly how a broken hashCode loses entries in a HashMap.

== asks “same object?” (identity). equals() asks “same value?” — but only if the class overrides it; the default Object.equals is just ==. The contract: if a.equals(b), then a.hashCode() == b.hashCode() must hold.

Override both, together, using the same fields. Why? A HashMap first picks a bucket by hashCode(), then confirms with equals(). If equal objects produce different hashes, they land in different buckets and the map can't find what it stored. (This is exactly why records, which generate both, are so handy.)

    

    
Reference equality vs logical equality

    
== compares references: are these two names pointing at the very same object on the heap? .equals is a method, so it can mean whatever the class decides — usually “same value.” The catch: Object’s default equals is literally this == other. So until you override it, value-equality and identity are the same thing, and two distinct-but-identical objects are “not equal.”

    

    
The equals contract: five rules, one classic trap

    
A correct equals must be reflexive (x.equals(x)), symmetric (x.equals(y) iff y.equals(x)), transitive, consistent (same answer every call, given unchanged fields), and return false for null (never throw). Symmetry is the one people break — typically by letting a subclass compare against its parent. Below, a plain Point can equal a ColorPoint but never the reverse, so equals disagrees with itself depending on the order.

    

    
The hashCode contract, and why you override both together

    
The rule is one-directional: equal objects MUST return the same hashCode; unequal objects may share one (a collision — allowed, just slower). It must also be consistent across calls while the object’s equals-relevant fields don’t change. Overriding equals but not hashCode is the cardinal sin: your objects are now “equal” yet scatter to different hashes, silently breaking every hash-based collection. Override the pair using the same fields.

    

    
How HashMap actually uses them: bucket, then confirm

    
A HashMap is an array of buckets. On put or get it takes the key’s hashCode, spreads the bits, and maps it to a bucket index — that’s the O(1) jump to the right shelf. Within that one bucket it walks the (usually tiny) list and uses equals to find the exact key. So hashCode chooses where to look and equals confirms what was found. Break the first and you never reach the right bucket; break the second and you can’t confirm the match.

    

    
Writing them correctly with java.util.Objects

    
Hand-written null checks are where bugs hide. Objects.equals(a, b) is null-safe (two nulls are equal, and it never NPEs), and Objects.hash(f1, f2, ...) combines any number of fields into one hash. One caveat: Objects.hash takes a varargs array, so it allocates on every call — fine almost everywhere, but on a hot path you should hand-roll the classic 31 * result + field loop to avoid the array.

    

    
Pitfalls: mutable keys, the getClass trap, and records

    
Two traps sink real code. First, never mutate a field used in equals/hashCode while the object is a key in a map or set — its hash changes, so it lands in the wrong bucket and becomes unreachable even by itself. Prefer immutable keys. Second, the instanceof-vs-getClass debate: instanceof can quietly break symmetry across subclasses (as shown earlier), while getClass() comparison guarantees symmetry but declares that no subclass can ever equal its parent. And the modern escape hatch: a record auto-generates a correct, matched equals/hashCode over all its components — reach for it when you just need a value type.

Coming from another language

    
What will surprise you

      
Coming from Python
Same idea: override __eq__ and __hash__ together, or sets and dicts misbehave. Java just makes it explicit on every class, and Objects.hash(...) mirrors Python's habit of hashing a tuple of fields.

      
Coming from JavaScript
JS Map/Set use reference identity for object keys and offer no value-equality hook — so this whole contract is unfamiliar. In Java, equal-by-value objects can serve as the same key, which is powerful but demands a correct hashCode.

      
Coming from C#
Directly analogous to overriding Equals and GetHashCode for Dictionary keys. Java's record ≈ C#'s record: both auto-generate a consistent pair so you don't have to.

  






  

    
Exercises

    
Make it stick

      
1 · The vanishing key
You override equals() but forget hashCode(), then use the object as a HashMap key. What goes wrong?
💡 Show hint
The default hashCode is identity-based, so two equal objects usually get different hashes and different buckets. get looks in the wrong bucket and returns null — the entry is effectively lost.

      
2 · Hash quality
Is hashCode() { return 1; } a correct implementation? Is it a good one?
💡 Show hint
Correct (equal objects share it, so the contract holds) but terrible: every key collides into one bucket, degrading the map to a linked list — O(n) lookups. A good hash spreads values across buckets.

      
3 · Mutating a key
You put an object into a HashSet, then change a field that equals/hashCode depend on. Why can set.contains(sameObject) now return false?
💡 Show hint
The set placed it in a bucket chosen by its original hash. Mutation changes the hash, so contains now computes a different bucket and looks in the wrong place — the object is stranded, unreachable even by its own reference. Moral: use immutable objects as keys.

      
4 · Symmetry across a subclass
ColorPoint extends Point and its equals also compares color, using instanceof Point. Why does this violate the contract, and which clause?
💡 Show hint
Symmetry. A plain Point p with the same x/y says p.equals(cp) is true (it ignores color), but cp.equals(p) is false (it demands matching color). Fixes: use getClass() equality (no cross-type equals), or favor composition over inheritance for value types.

      
5 · Objects.hash on a hot path
Objects.hash(a, b, c) is clean and correct. Why might a profiler flag it inside a tight loop, and what do you replace it with?
💡 Show hint
Objects.hash takes Object... varargs, so each call boxes primitives and allocates a temporary array. In hot code that is measurable GC pressure. Hand-roll the standard accumulation: int h = 1; h = 31*h + Integer.hashCode(a); ... — no array, no boxing.
