Exactly one of something

Real-world picture: a country has exactly one sitting president. No matter who asks “who’s the president?”, everyone gets the same person. The Singleton pattern guarantees a class has just one instance and gives everyone a single, shared way to reach it.

Concept

One instance, one global access point

🏷 Real-world analogy

A Singleton is the one printing press that mints a country’s currency. There may be millions of people who need banknotes, and countless bank branches asking for them — but there is exactly one official press, and every request is routed back to that same machine. You cannot buy your own and start printing (the constructor is private); you ask the treasury for access (a static accessor), and it always hands you a note from the same press. Because everyone shares that one source, the money supply stays consistent — but it also means the whole economy depends on a single hidden authority, which is exactly why over-using Singletons makes a system rigid and hard to test.

Some things should exist only once: an app’s configuration, a connection pool, a logger. Singleton makes the class itself responsible for that. The trick: make the constructor private so no one can new it, create the one instance internally, and hand it out through a static method.

The enum form is the idiom most Java pros prefer — the JVM guarantees a single instance for free. A caution: a Singleton is global state, so overusing it makes code hard to test. Reach for it when “exactly one” is a genuine rule, and prefer dependency injection (module 29) when you just want to share an object.

    


    
Intent: guarantee one instance + a global access point

    
The Gang of Four define Singleton as two guarantees at once: ensure a class has only one instance, and provide a global point of access to it. Both halves matter. It is legitimate when a single instance models a real constraint — a hardware device driver, an in-process cache, a thread pool, an app-wide configuration — where a second copy would be wrong, not merely wasteful. If you only want convenient sharing of one object, that is a job for dependency injection, not this pattern.



    
Naive lazy init — and why it is NOT thread-safe

    
A common first attempt defers creation until the first call (“lazy”) with a plain null check. On a single thread it works. Under concurrency it is broken: two threads can both evaluate instance == null as true before either assigns, so the constructor runs twice and each thread walks away with a different object — violating the entire point of the pattern.



    
Correct: eager static final and double-checked locking

    
The simplest correct form is eager initialization: a private static final field. Class initialization runs inside the JVM’s own lock, so the instance is published safely and exactly once — the cost is that it is built even if never used. If you truly need laziness with a lock, use the double-checked locking idiom, which requires volatile on the field. Without volatile, another thread can observe a partially-constructed object because the write of the reference can be reordered ahead of the object’s field writes.



    
The initialization-on-demand HOLDER idiom

    
The cleanest lazy-and-thread-safe form uses a private static holder class. A nested class is not loaded until it is first referenced, so INSTANCE is created only when get() is first called. The JVM’s class-initialization lock makes that creation atomic and correctly published — with no explicit synchronization and therefore no locking cost on subsequent calls.



    
The enum singleton (Effective Java’s recommendation)

    
Joshua Bloch’s Effective Java calls a single-element enum the best way to implement a singleton. The JVM guarantees exactly one instance of each enum constant, and it is thread-safe for free. Crucially it is also serialization-proof (enums serialize by name, so deserializing never fabricates a second object) and reflection-proof (the reflection API explicitly forbids constructing enum instances) — two attacks that can break the plain class-based forms.



    
Downsides: global state, and preferring dependency injection

    
A Singleton is global, mutable state reached implicitly. That hurts testability (tests cannot swap in a fake or reset it between runs), hides dependencies (a class that calls Foo.get() internally doesn’t declare it needs a Foo), and couples code to a concrete type. The modern default is dependency injection: register the class as singleton-scoped in a DI container (Spring, Guice) and let it inject the one instance through the constructor. You get “exactly one, shared” without the private-constructor baggage — and tests just pass a mock.



    
Singletons in the JDK

    
The pattern is all over the standard library. Runtime.getRuntime() always returns the one Runtime bound to the JVM; Desktop.getDesktop() and Toolkit.getDefaultToolkit() follow the same shape. And the smallest singletons of all are the JDK’s stateless ones — Collections.emptyList() and Comparator.naturalOrder() hand back a shared instance because there is no reason to allocate more than one.

Coming from another language

    
What will surprise you

      
Coming from Python
A Python module is itself a singleton — import it anywhere and you share one namespace, so people often just use a module-level object. The explicit pattern uses a classmethod or __new__ guard, but it’s needed far less.

      
Coming from JavaScript
An ES module (or a single exported object literal) is a natural singleton — every import gets the same instance. Java needs the private-constructor ceremony because every class is instantiable by default.

      
Coming from C#
Same idea: a private constructor + static instance, or Lazy<T> for thread-safe lazy init. A static class is the “no instance at all” cousin. The Java enum trick has no direct C# equivalent.

  






  

    
Exercises

    
Make it stick

      
1 · Why private constructor?
What stops calling code from just writing new Settings() and making a second instance?
💡 Show hint
The private constructor — it’s only accessible inside the class itself, so external code can’t invoke it. The single instance is created internally and handed out via the static accessor.

      
2 · The hidden cost
Why can heavy use of Singletons make a codebase hard to unit-test?
💡 Show hint
A Singleton is global, shared, mutable state reached implicitly (not passed in), so tests can’t easily substitute a fake or reset it between runs. Prefer injecting the dependency (DI) when you only need sharing, not a hard “exactly one” guarantee.

      
3 · The race condition
In the naive lazy if (instance == null) instance = new X();, describe the exact interleaving of two threads that produces two instances.
💡 Show hint
Thread A evaluates instance == null → true, then is paused before it assigns. Thread B now runs the whole method: it also sees null, constructs an object, and assigns it. Thread A resumes and constructs a second object, overwriting the field. The two threads hold different references — the “single” guarantee is gone. The fix is a lock (DCL with volatile), the holder idiom, an eager field, or an enum.

      
4 · Why volatile?
Double-checked locking works only if the instance field is volatile. What can go wrong without it, even though there is a synchronized block?
💡 Show hint
Without volatile, the write that publishes the reference can be reordered ahead of the writes that initialize the object’s fields. A second thread taking the fast path (no lock) can then read a non-null reference to a partially-constructed object. volatile forbids that reordering and establishes the happens-before edge that makes the fully-built object visible.

      
5 · Enum vs class
Two ways a plain class-based singleton can be broken into producing a second instance — and why the single-element enum defeats both.
💡 Show hint
Serialization: deserializing a class-based singleton creates a fresh object unless you add readResolve(). Reflection: setAccessible(true) on the private constructor lets attackers call newInstance(). An enum is immune to both: enums serialize by name (no new object), and the reflection API explicitly refuses to instantiate enum types. That is why Effective Java recommends it.
