State and behavior that belong to the class, not the object

Every Java program starts in a static method — main. Static members belong to the class itself, shared across all instances. Used well they give you constants, factories, and utilities; used carelessly they become global mutable state that wrecks testability.

Concept

One copy for the class, not one per object

🏷 Real-world analogy

A static member is the town clock on the square. There is exactly one clock for the whole town, mounted on the class itself — every resident glances up and reads the same time, and if the town adjusts it, everyone sees the change at once. An instance member is each resident’s own wristwatch: one per person, set independently, invisible to the neighbours. A static method is a notice pinned to the public board — a procedure anyone can follow without needing a particular resident to carry it out (no this). The trap: if that one town clock is freely resettable by anyone passing by (mutable static state), the whole town argues about what time it really is — that is why shared mutable statics wreck testability and thread-safety.

An instance field exists once per object; a static field exists once per class, shared by every instance. A static method has no this — it can’t touch instance state, which makes it perfect for stateless utilities and factory methods.

Good uses: constants (static final), factory methods (List.of, Integer.valueOf), and pure utilities (Math.max). A static initializer block runs once when the class loads. The danger: static mutable state is global state — it’s shared everywhere, hard to reset between tests, and unsafe under concurrency. Keep static things either constant or stateless.

    

    
Static fields: one shared slot per class

    
An instance field is allocated inside every object on the heap; a static field is allocated once, in the class metadata, when the class is loaded. That single slot is why statics are the natural home for counters, caches, and registries that must span all instances. Read or write it through the class name — Counter.created — not through an object reference, or reviewers will assume it is instance state.



    
Static methods have no this — and can’t be overridden

    
Because a static method is attached to the class rather than an object, it has no this and cannot touch instance fields — ideal for pure utilities (Math.max) and factory methods (List.of). It also is not polymorphic: a static method in a subclass with the same signature hides the parent’s, it does not override it. Which one runs is decided at compile time by the static type of the reference, so a static call never dispatches dynamically.



    
static final constants and the naming convention

    
A field marked static final is a genuine constant: one shared slot that can be assigned exactly once. For primitives and Strings initialised with a compile-time constant, the compiler inlines the value straight into callers. Convention names such constants in UPPER_SNAKE_CASE. Beware the classic trap: final only freezes the reference, so a static final pointing at a mutable object (a list, an array) is still globally mutable through that reference.



    
Static initializer blocks and lazy class initialization

    
When a field needs more than a one-liner to set up, a static { ... } block runs the setup exactly once. All static field initialisers and static blocks execute top-to-bottom during class initialization — which the JVM triggers lazily, on first active use of the class (first instance, first static-field read, first static-method call), not merely when it is loaded. This is the mechanism behind the initialization-on-demand holder idiom for thread-safe lazy singletons.



    
Static nested classes vs inner classes

    
A nested class marked static is just a top-level class scoped inside another for packaging — it holds no hidden reference to an enclosing instance. A non-static inner class does: every inner object silently pins the outer object it was created from, which quietly extends that outer object’s lifetime and can leak memory. Prefer static nested classes unless you genuinely need access to the enclosing instance’s fields.



    
import static for readable calls

    
import static pulls a class’s static members into scope so you can name them unqualified — writing max(a, b) instead of Math.max(a, b). It shines for test assertions (assertEquals) and math-heavy code, but used broadly it hides where a method comes from and invites name clashes, so import the specific members you use rather than a wildcard.

Coming from another language

    
What will surprise you

      
Coming from Python
Java’s static fields ≈ Python class attributes, and static methods ≈ @staticmethod (a method bound to the class, no self). Java has no module-level functions — a free function becomes a static method on a class.

      
Coming from JavaScript
JS classes have static fields/methods too, and module-scope values play the role Java gives static. The same warning applies in both: a shared mutable static/module variable is global state and a testing headache.

      
Coming from C#
Nearly one-to-one: static fields/methods, const/static readonly for constants, and static constructors ≈ Java’s static initializer blocks. Same guidance about avoiding shared mutable static state.

  






  

    
Exercises

    
Make it stick

      
1 · Static or instance?
A formatCurrency(long cents) helper uses no object state. Should it be static or an instance method?
💡 Show hint
Static. It depends only on its arguments, not on any object’s fields, so it needs no this. Making it static signals “pure utility” and lets callers use it without constructing an instance.

      
2 · The testing trap
A class keeps a static Map cache that tests mutate. Why do the tests start failing intermittently?
💡 Show hint
The static cache is shared across all tests and persists between them, so one test’s entries leak into another — order-dependent, flaky failures. Static mutable state is global state; prefer instance state you can recreate per test (or reset it explicitly).

      
3 · Hidden, not overridden
Both Base and Derived declare static String who(). With Base b = new Derived();, what does b.who() print, and why?
💡 Show hint
It prints "Base". Static methods are resolved at compile time by the declared type of the reference (Base), not the runtime object. This is method hiding, not overriding — statics are never polymorphic. Call them by class name to avoid the confusion.

      
4 · The final array that isn’t constant
static final int[] PRIMES = {2,3,5,7}; is declared final. Can another class do PRIMES[0] = 99;? What does final actually protect here?
💡 Show hint
Yes, it compiles and mutates the array. final freezes only the reference — you can’t reassign PRIMES to a different array — but the array’s contents stay writable. For a genuinely immutable shared constant use List.of(2,3,5,7).

      
5 · static nested or inner?
You’re writing a small Node helper class inside a LinkedList that never needs the list’s own fields. Should it be a static nested class or a (non-static) inner class, and why does it matter?
💡 Show hint
Static nested. A non-static inner class silently holds a reference to the enclosing LinkedList instance, which wastes a pointer per node and can keep the whole list alive longer than intended (a memory-leak risk). Since Node needs nothing from the outer instance, static makes it self-contained. That’s exactly what the JDK’s own collections do.
