A stand-in that controls access

Real-world picture: a debit card stands in for the cash in your bank account. It looks and acts like access to your money, but it can check your PIN, enforce limits, and only reaches the real account when needed. A Proxy is a placeholder that controls access to another object.

Concept

Same interface, with a gatekeeper in front

🏷 Real-world analogy

A proxy is a celebrity’s personal assistant. You call the star’s office with the same request you’d make of the star directly — “can you do this shoot Friday?” — but you reach the assistant, who presents the exact same interface as the star. The assistant decides what happens to your call: forward it to the star, schedule it for later because the star isn’t “created” for this until needed (lazy), screen it if you’re not on the approved list (access control), or log it in the calendar. You never notice the difference — the assistant answers with the same “interface” the star would — yet every real interaction is controlled. That is a Proxy: same interface as the real subject, standing in front to control access to it.

A proxy implements the same interface as the real object and holds a reference to it (or creates it on demand). Callers think they’re talking to the real thing, but the proxy can add access control, caching, logging, or — very commonly — lazy loading of an expensive object.

Java leans on proxies heavily: Hibernate returns proxies for lazy entity loading, Spring wraps beans in proxies to add transactions and security, and java.lang.reflect.Proxy builds them at runtime. The client code never changes — the proxy slips in transparently.

    


    
The intent: a stand-in that controls access

    
The Gang of Four define a proxy as a surrogate for another object that controls access to it. The crucial constraint: the proxy implements the same interface as the real subject, so it is a drop-in replacement. Callers hold a reference typed as the interface and cannot tell whether they have the real object or a stand-in. Everything the proxy adds — a permission check, a cache lookup, a log line, a deferred construction — happens around a delegation to the real subject.



    
The four flavors of proxy

    
The pattern is one shape with several jobs. A virtual proxy defers creating an expensive object until it is first used (lazy loading). A protection proxy enforces access control, rejecting callers who lack permission. A remote proxy is a local stub for an object that actually lives in another JVM or on another machine, hiding the network call. A logging or caching proxy records access or memoizes results. Same structure, different reason to intercept.



    
A worked static proxy

    
A static proxy is one you write by hand: a class that implements the interface, holds the real subject, and wraps each method with extra behavior before (or after) delegating. It is explicit and easy to read, but you must write one method per interface method — add a method to the interface and every hand-written proxy must be updated. This example adds logging and caches the first result.



    
Java’s dynamic proxies

    
Writing a class per interface is tedious, so Java ships a runtime proxy generator: java.lang.reflect.Proxy.newProxyInstance synthesizes a class implementing any set of interfaces on the fly. Every method call on the generated object is routed to a single InvocationHandler.invoke(proxy, method, args), where you add your behavior and call method.invoke(real, args) to delegate. One handler covers every method — add a method to the interface and the proxy handles it automatically. The catch: JDK dynamic proxies only work for interfaces; proxying a concrete class needs bytecode libraries like CGLIB or ByteBuddy.



    
How frameworks lean on proxies

    
Proxies are the quiet engine behind much of the Java ecosystem. Spring AOP wraps your beans in proxies to weave in cross-cutting concerns: a @Transactional method is really a proxy that opens a transaction, calls your method, and commits or rolls back — which is why calling one @Transactional method from another within the same bean skips the proxy and the transaction. Hibernate returns proxy entities for lazy associations, loading the row from the database only when you first touch a field. Mocking libraries like Mockito generate proxies that record calls and return stubbed answers instead of running real code.



    
Proxy vs Decorator

    
Structurally they are twins: both wrap an object and share its interface. The difference is intent. A Decorator adds behavior — you deliberately stack wrappers to compose new features (buffering, compression) and the decorator always talks to a subject it was handed. A Proxy controls access to a subject it typically owns or creates — it may decide whether and when to call the real object at all (deny it, defer it, cache past it). Decorator says “same object, more powers”; Proxy says “same interface, guarded gateway.”

Coming from another language

    
What will surprise you

      
Coming from Python
__getattr__ and descriptors let an object impersonate another and intercept access — a natural proxy. @property lazily computes a value much like a virtual proxy defers loading.

      
Coming from JavaScript
JS has a built-in Proxy object that intercepts property access and method calls — the pattern is a language feature. Java builds proxies via interfaces or reflect.Proxy at runtime.

      
Coming from C#
DispatchProxy and libraries like Castle DynamicProxy create runtime proxies; EF and DI frameworks use them for lazy loading and interception, mirroring Hibernate/Spring in Java.

  






  

    
Exercises

    
Make it stick

      
1 · Proxy vs Decorator
Both wrap an object with the same interface. How does a Proxy differ in intent from a Decorator?
💡 Show hint
A Decorator adds new behavior/features to the object. A Proxy controls access to it — lazy loading, permissions, caching, remoting — usually without changing what the object does. Same shape, different purpose.

      
2 · Where would it help?
A page shows 100 high-res images but users scroll past most. How does a virtual proxy help?
💡 Show hint
Each image is a proxy that holds only the file path and a placeholder. The heavy bytes load lazily when an image actually scrolls into view, so you never pay to load the ones nobody sees.

      
3 · Why an InvocationHandler?
With a hand-written static proxy you write one method per interface method. What does java.lang.reflect.Proxy give you instead, and what is its main limitation?
💡 Show hint
A dynamic proxy routes every method call to a single InvocationHandler.invoke(proxy, method, args), so one handler covers the whole interface — and any method you later add. The limitation: JDK proxies only implement interfaces. To proxy a concrete class you need a bytecode library like CGLIB or ByteBuddy.

      
4 · The self-invocation trap
A Spring bean has a @Transactional method a() that calls another @Transactional method b() on this. Why might b() not run in its own transaction?
💡 Show hint
The transaction is added by a proxy that wraps the bean. A caller from outside goes through the proxy, but this.b() is a direct call on the target object — it never touches the proxy, so its transactional advice is skipped. Fixes: call through an injected self-reference, or split b() into a separate bean.

      
5 · Pick the flavor
Match each need to a proxy flavor: (a) hide that an object lives on another server; (b) skip an expensive DB load until a field is read; (c) reject callers without a role; (d) memoize repeated lookups.
💡 Show hint
(a) remote proxy — a local stub for a remote object; (b) virtual proxy — lazy creation/loading (Hibernate does this); (c) protection proxy — access control; (d) caching proxy — return a stored result instead of delegating. All share one interface with the real subject.
