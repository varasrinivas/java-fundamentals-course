Order a product without naming the class

Real-world picture: you walk into a pizza place and order “a veggie pizza.” You don’t reach into the kitchen and assemble it yourself — the store decides exactly how to make it. Factory Method puts object creation behind a method so callers ask for what they want, not how to build it.

Concept

Defer the “new” to a method subclasses control

🏷 Real-world analogy

A factory method is ordering the chef’s choice at a restaurant. You tell the waiter “bring me a dessert” — a category, not a recipe. The kitchen decides and builds the concrete dish: tonight it plates a lava cake, tomorrow a tiramisu. You, the caller, never write new ChocolateCake(); you only depend on the idea of “a dessert.” Because creation lives behind the kitchen door, the restaurant can change what it serves — new supplier, seasonal menu, a healthier recipe — without you changing your order at all. That indirection between what you ask for and which concrete class gets built is the whole pattern.

Hardcoding new VeggiePizza() everywhere couples your code to concrete classes. A factory method wraps the new in an overridable method, so subclasses (or configuration) decide which concrete type to create, and callers depend only on an interface.

You see factory methods all over the JDK: List.of(...), Integer.valueOf(...), LocalDate.now(). They give better names than constructors, can return cached instances, and can hand back a subtype — flexibility a raw constructor can’t.

    


    
Intent: depend on an abstraction, not on new

    
The Gang of Four define Factory Method as: “define an interface for creating an object, but let subclasses decide which class to instantiate.” The point is to invert a dependency. Client code is written against a product interface and calls a creation method; the decision of which concrete class to build is pushed to a subclass or configuration. Swap the concrete type and the client never changes.




    
The participants (a small worked example)

    
Classic Factory Method has four roles: the Product interface, one or more Concrete Products, an abstract Creator that declares the factory method (and usually calls it), and Concrete Creators that override it to pick a class. The creator often contains real logic that uses the product it just made — that is what separates this from a bare factory function.




    
Simple factory vs Factory Method vs Abstract Factory

    
These three get muddled. A simple factory is just a static method with a switch — convenient, but not a GoF pattern and not extensible without editing it. Factory Method (this module) uses inheritance: subclasses override one creation method. Abstract Factory (module 46) goes further — an object whose methods create a whole family of related products that must fit together.




    
Static factory methods: the everyday Java form

    
You rarely build the full inheritance ceremony. The version you meet daily is the static factory method — a static method that returns an instance instead of a public constructor. The JDK is saturated with them, and Effective Java item 1 recommends considering them before constructors.




    
Why a static factory beats a constructor

    
Constructors have three hard limits a static factory escapes. (1) They can’t be named — every overload is just new Foo(...), so BigInteger.probablePrime(n, rnd) reads far better than a constructor. (2) They must return a fresh object of exactly their class — a factory can cache and hand back a shared instance (Integer.valueOf, Boolean.valueOf). (3) They must return their own type — a factory can return any subtype, even one that’s package-private, which is how List.of hides its real implementation class.




    
When it helps — and when it’s over-engineering

    
Reach for a factory when creation logic is non-trivial or likely to vary: choosing an implementation by config, returning cached/pooled objects, or injecting a fake in tests (a factory is a natural seam — pass a stub creator). But a factory around a single, stable new Point(x, y) is pure ceremony. If there’s one implementation and no naming/caching/subtype benefit, just call the constructor. Patterns are a response to change; add the indirection when the change actually shows up.

Coming from another language

    
What will surprise you

      
Coming from Python
With duck typing you often skip interfaces and just use a factory function that returns whatever object fits. Java’s version is more formal (an interface + an overridable method) but achieves the same decoupling.

      
Coming from JavaScript
A plain factory function returning an object is the everyday JS equivalent — no class required. Java leans on an interface return type so the compiler enforces the contract.

      
Coming from C#
Nearly identical — a virtual/abstract factory method or a static factory. C#’s static creation methods (e.g. Task.FromResult) mirror Java’s List.of / valueOf style.

  






  

    
Exercises

    
Make it stick

      
1 · Why not a constructor?
Give two things a static factory method can do that a plain constructor cannot.
💡 Show hint
It can have a meaningful name (List.of vs another overload), return a cached or shared instance instead of always allocating, and return a subtype of the declared type. Constructors must create a new object of exactly their class.

      
2 · Spot the coupling
Code is littered with new MySqlConnection(). How does a factory method make swapping to Postgres easier?
💡 Show hint
Centralize creation in one factory that returns a Connection interface. Callers depend on the interface, so switching databases means changing one factory, not every new call site.

      
3 · Name the participants
In the App / Dialog example, label each of the four roles: Product, Concrete Product, Creator, Concrete Creator.
💡 Show hint
Dialog is the Product interface; HtmlDialog / WinDialog are Concrete Products; the abstract App (declaring createDialog() and using it in show()) is the Creator; WebApp / DesktopApp are Concrete Creators that override the factory method.

      
4 · Factory Method vs Abstract Factory
You need to create a matching set of Button, Checkbox, and Menu that all share a theme (dark vs light). Is Factory Method enough, or do you want Abstract Factory?
💡 Show hint
You want Abstract Factory (module 46). Factory Method produces one product per creation method; here you need a family of related products guaranteed to fit together (all dark, or all light). One ThemeFactory object with button(), checkbox(), menu() keeps them consistent.

      
5 · When NOT to add a factory
A teammate wraps every new Point(x, y) in a PointFactory.create(x, y) that only does return new Point(x, y);. Justified, or over-engineering?
💡 Show hint
Over-engineering. There’s a single stable implementation and no naming, caching, or subtype benefit — the factory adds indirection for zero payoff. A static factory earns its keep only when creation varies, can be cached/pooled, needs a descriptive name, or must return a hidden subtype. Otherwise just call the constructor.
