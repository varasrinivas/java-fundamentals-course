println is not a logging strategy

In production you can't attach a debugger — logs are how you see what happened. Java's ecosystem settled on SLF4J as a facade over backends like Logback. Levels, parameterized messages, and structure separate useful logs from noise.

Concept

A facade, levels, and lazy messages

🏷 Real-world analogy

Logging is your aircraft’s black-box flight recorder. When something goes wrong at 30,000 feet (in production, where you can’t attach a debugger), nobody replays the flight live — investigators pull the recorder afterward and reconstruct what happened, second by second. Log levels are the cockpit’s severity triage: a flickering light is a DEBUG curiosity, a low-fuel warning is WARN, and a full mayday is ERROR — you tune how much chatter the recorder keeps. And SLF4J is the universal power adapter: your code plugs into one standard socket, and whatever electrical grid the destination airport provides (Logback, Log4j2, java.util.logging) lights up without you rewiring the plane.

Code against the SLF4J facade (Logger, LoggerFactory); pick a backend (Logback, Log4j2) at deploy time. Each message has a level — ERROR, WARN, INFO, DEBUG, TRACE — and a configured threshold drops anything less severe.

Use {} placeholders, not string concatenation: the message is only formatted if the level is enabled, so a disabled debug call costs almost nothing. Log the exception object (last argument) to capture the stack trace, never log secrets or PII, and prefer structured/JSON logs so tools can search them.

    


    
Why System.out.println fails in production

    
println is a debugging reflex, not a strategy. It has no levels, so you can’t dial the noise up or down — the only volume control is deleting the line and redeploying. It has no routing: everything piles onto stdout instead of a rolling file or a log aggregator. It carries no timestamp, thread name, or source unless you concatenate them by hand. It is always eager (the string is built even when no one reads it) and System.out is a synchronized PrintStream, so a chatty loop can actually throttle throughput.

    


    
The ecosystem: SLF4J facade vs backends

    
SLF4J (Simple Logging Facade for Java) is an API only — a set of interfaces you code against. At runtime it binds to exactly one backend that does the real work: Logback (written by the same author, the common default), Log4j2, or a bridge to the JDK’s built-in java.util.logging (JUL). Because libraries log through the facade, the application chooses the implementation by picking a dependency — no call site changes.

    


    
Log levels — and choosing the right one

    
The five standard SLF4J levels form a severity ladder: ERROR > WARN > INFO > DEBUG > TRACE. A configured threshold keeps everything at or above it and drops the rest. Choosing well is the whole game: ERROR means a human should look; WARN is recoverable but suspicious; INFO is the business/lifecycle narrative; DEBUG and TRACE are developer diagnostics you enable only when hunting a bug.

    


    
Parameterized logging beats concatenation

    
Pass a message template with {} placeholders and the values as trailing arguments. This does two things at once: it keeps call sites readable, and — crucially — if the level is disabled, SLF4J returns immediately without formatting the string or calling toString() on the arguments. That makes a switched-off debug call essentially free, so the old if (log.isDebugEnabled()) guard is only worth it when computing an argument is itself expensive.

    


    
A logger per class

    
The convention is one private static final Logger per class, obtained from LoggerFactory.getLogger(Foo.class). Passing the Class names the logger after its fully-qualified class name, which does two jobs: every log line records where it came from, and your configuration can raise or lower the level for a whole package (com.shop) or a single class without touching code.

    


    
Operational hygiene: exceptions, secrets, MDC

    
Three habits separate useful logs from liabilities. First, log the exception object as the last argument — log.error("...", e) — so SLF4J captures the full stack trace; e.getMessage() alone throws it away. Second, never log secrets or PII (passwords, tokens, card numbers, full emails) — logs are copied, shipped, and indexed far more widely than you think. Third, use MDC (Mapped Diagnostic Context) to stamp a correlation key like a request ID onto every line on the current thread, so you can trace one request across many log statements — and always clear() it, because threads are pooled and reused.

Coming from another language

    
What will surprise you

      
Coming from Python
SLF4J + Logback ≈ the logging module: getLogger(__name__), levels, handlers. SLF4J's {} placeholders are like logger.info("%s", x) lazy formatting — the string is built only if the level is on.

      
Coming from JavaScript
A step up from console.log toward Winston/Pino. The SLF4J facade lets you swap backends without touching call sites, and levels + thresholds give you the production filtering raw console lacks.

      
Coming from C#
SLF4J is the ILogger abstraction; Logback/Log4j2 ≈ Serilog/NLog providers. Parameterized log.info("{}", x) mirrors structured logging's Log.Information("{X}", x) — message template now, values captured separately.

  






  

    
Exercises

    
Make it stick

      
1 · Why {} not +?
What's the difference between log.debug("cart: " + cart) and log.debug("cart: {}", cart) when DEBUG is disabled?
💡 Show hint
The first always builds the string (calling cart.toString()) even though it's discarded — wasted work. The {} form skips formatting entirely when DEBUG is off, so it's essentially free.

      
2 · Capture the trace
In a catch block you write log.error("failed: " + e.getMessage()). What valuable thing did you lose?
💡 Show hint
The stack trace. Pass the exception as the last argument instead: log.error("failed for order {}", orderId, e). SLF4J then logs the full trace, which getMessage() alone discards.

      
3 · Facade vs backend
Your code imports only org.slf4j.Logger, yet at runtime it must actually write somewhere. What decides where the lines go, and how do you switch it?
💡 Show hint
SLF4J is just the facade (API). The backend on the classpath — Logback, Log4j2, or a JUL bridge — does the real writing. You switch it by swapping that one dependency; your call sites, which only touch SLF4J, never change.

      
4 · Is the guard still needed?
Someone reviews your code and asks you to wrap every log.debug("id={}", id) in if (log.isDebugEnabled()). Are they right?
💡 Show hint
No. With {} parameters, a disabled debug call already returns without formatting the string or calling toString(). The guard only earns its keep when building an argument is itself expensive — e.g. log.debug("dump={}", serializeWholeState()).

      
5 · Pick the level
Assign a level to each: (a) the app finished startup and is listening on a port; (b) a retry succeeded on the 3rd attempt; (c) the database is completely unreachable; (d) the exact SQL bound-parameter values on every query.
💡 Show hint
(a) INFO — a key lifecycle event. (b) WARN — recoverable but worth noticing. (c) ERROR — a human must act. (d) DEBUG or TRACE — firehose diagnostics, off in production (and mind PII in those values).
