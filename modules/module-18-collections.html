Lists, Sets and Maps, and when to pick which

Java ships a small, well-worn set of data structures behind three interfaces: List, Set, and Map. Knowing how HashMap finds a key in O(1) — and when it degrades — is core Java literacy.

Concept

Three interfaces, a handful of workhorse classes

🏷 Real-world analogy

The collections are different kinds of storage furniture. A List is a numbered row of shelves — things stay in the order you placed them, shelf 3 is reachable instantly by number, and nothing stops you putting the same book on two shelves (ordered, indexed, duplicates allowed). A Set is a bag with a bouncer: try to drop in a duplicate and it silently rejects it, so every element is unique. A Map is a labelled filing cabinet (a dictionary): you never scan the drawers, you look up a folder by its key and pull out the value in one move. A Queue/Deque is a line of people — you join at one end and are served from the other. Pick the furniture by how you need to store and reach your data, then let Java worry about the mechanics.

Program to the interface, choose the implementation for its performance: List (ordered, indexed — usually ArrayList), Set (no duplicates — HashSet), Map (key→value — HashMap).

A HashMap turns a key into an array index: take the key's hashCode(), spread its bits, and reduce modulo the bucket count. Two keys landing in one bucket is a collision, handled by a short chain (which becomes a tree if it grows). When the table gets too full it resizes and rehashes.

    


    
The hierarchy: Collection vs Map

    
The framework has two roots, not one. Collection<E> is the supertype of List, Set and Queue — anything that holds a bunch of individual elements. Map<K,V> is deliberately not a Collection: it stores key→value pairs, not single elements, so it lives on its own branch. That is why you can iterate a List directly but must go through keySet(), values() or entrySet() to walk a Map.




    
ArrayList vs LinkedList

    
ArrayList is a growable array: elements sit in one contiguous block, so get(i) is O(1) and iteration is cache-friendly. LinkedList is a doubly-linked chain of nodes: O(1) insert/remove once you already hold the node, but get(i) is O(n) because it walks the chain. In practice ArrayList wins almost always — even for queue-like use, ArrayDeque beats LinkedList. Reach for LinkedList only for a genuine list you constantly splice in the middle.




    
The Set family: Hash, Linked, Tree

    
All three reject duplicates; they differ only in iteration order and cost. HashSet is fastest (O(1) average) but iterates in an unpredictable order. LinkedHashSet keeps a linked list alongside the buckets so it iterates in insertion order, for a small memory cost. TreeSet is a red-black tree: it keeps elements sorted and offers range queries (first, ceiling, headSet), but every operation is O(log n) and elements must be Comparable (or you supply a Comparator).




    
The Map family mirrors the Sets

    
The Map implementations line up one-to-one with the Sets, because a HashSet is literally a HashMap with dummy values. HashMap gives O(1) average lookup with no order; LinkedHashMap preserves insertion order (and, with accessOrder=true, makes a ready-made LRU cache); TreeMap keeps keys sorted with O(log n) navigation. HashMap permits one null key and null values; TreeMap forbids null keys (it must compare them).




    
Fail-fast iterators & safe removal

    
Most collections return fail-fast iterators: if the collection is structurally modified while you iterate (via anything other than the iterator itself), they throw ConcurrentModificationException — a best-effort guard against subtle bugs, not a concurrency feature. To remove while looping, use Iterator.remove() or the one-liner removeIf.




    
Immutable factories: List.of, Set.of, Map.of

    
Since Java 9, List.of(...), Set.of(...) and Map.of(...) build compact unmodifiable collections in one line. They are stricter than the old collections: any mutating call throws UnsupportedOperationException, and they reject null elements/keys/values outright. Use them for constants and defensive copies; wrap them in new ArrayList<>(...) when you need a mutable version.




    
Ordering: Comparable vs Comparator

    
Comparable<T> defines a type's natural order from the inside, via compareTo (this is what TreeSet and Collections.sort use by default). A Comparator<T> is an external ordering you pass in, letting you sort the same type many ways without touching it. Modern comparators compose fluently with comparing, thenComparing and reversed.




    
Prefer ArrayDeque over Stack and Vector

    
Vector and its subclass Stack are Java 1.0 relics: every method is synchronized, so you pay for locking even single-threaded, and Stack extends Vector so it exposes index access that breaks stack semantics. For a stack or queue today, use ArrayDeque — it is faster, unsynchronized, and implements Deque so it works as both. If you need thread safety, reach for java.util.concurrent types instead.

Coming from another language

    
What will surprise you

      
Coming from Python
HashMap ≈ dict, ArrayList ≈ list, HashSet ≈ set. Big difference: Java's HashMap does not preserve insertion order — use LinkedHashMap for that (Python dicts are ordered by default).

      
Coming from JavaScript
Java's Map is a real interface with many implementations; JS's Map is one built-in. And Java keys use equals()/hashCode(), so two distinct objects that are equal collide as the same key — unlike JS's identity-based Map keys.

      
Coming from C#
Dictionary<K,V> ≈ HashMap, List<T> ≈ ArrayList. Java separates the interface (Map) from the class (HashMap) more strictly, so you'll often declare the interface and instantiate the class.

  






  

    
Exercises

    
Make it stick

      
1 · Pick the structure
You need to remember which user IDs you've already emailed, and ask “did I email 4187?” millions of times. Which collection?
💡 Show hint
A HashSet<Integer> (or a Set). Membership tests are O(1) average, and you don't care about order or duplicates — exactly a Set's job.

      
2 · The broken key
You use a mutable object as a HashMap key, then change a field used in its hashCode(). Why can you no longer find it?
💡 Show hint
Its hash now points to a different bucket than where it was stored, so get looks in the wrong place. Map keys must be effectively immutable in their hashed fields.

      
3 · Order matters
You build a Map of config keys and print it back to a user; the keys must appear in the exact order they were added. Which Map implementation, and why not plain HashMap?
💡 Show hint
Use LinkedHashMap: it keeps a linked list of entries in insertion order. A plain HashMap gives no order guarantee — iteration order depends on hashes and capacity and can change on resize. If instead you wanted the keys sorted, you'd use TreeMap.

      
4 · Remove while looping
This loop throws ConcurrentModificationException:
for (String s : list) if (s.isBlank()) list.remove(s);
Give two correct ways to strip the blank strings.
💡 Show hint
(1) The one-liner list.removeIf(String::isBlank). (2) An explicit Iterator and it.remove(). Both mutate the list through the iterator, so the fail-fast check doesn't trip. The enhanced for uses an iterator under the hood, and removing behind its back is what it detects.

      
5 · Guard a constant
You expose List<String> DEFAULTS as a public constant and want callers unable to mutate it. What do you use, and what happens if a caller calls add?
💡 Show hint
Build it with List.of(...) (or wrap in Collections.unmodifiableList). Any mutating call — add, set, remove — throws UnsupportedOperationException. Bonus: List.of also rejects null elements, so the constant can never contain one.
