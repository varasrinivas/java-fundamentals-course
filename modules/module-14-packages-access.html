Who can see your code

Packages give every Java type a globally unique name and a unit of encapsulation. The four access levels — public, protected, package-private, private — decide who may touch what. Get them right and your API surface stays small on purpose.

Concept

Four levels, from wide open to sealed shut

🏷 Real-world analogy

A package is a postal address; access modifiers are who holds the keys. Every class lives at a unique address built from a reverse-domain street name — com.acme.billing.Invoice is as globally unique as a mailing address, and the folder tree com/acme/billing/ is literally that address written on disk. Inside the building, the four access levels are the keys you hand out: private is your own locked office (only this class), package-private opens the doors on your floor (the same package), protected also lets in family — your subclasses — alongside the floor, and public is the open public lobby anyone can walk into. A JPMS module is the building’s front desk: even a public room stays sealed to outsiders unless the module exports that floor.

A package is a namespace, mirrored by folders: com.acme.billing.Invoice lives in com/acme/billing/Invoice.java. Within and across packages, four modifiers gate access:

The default — no modifier — is package-private, not public; it's Java's quiet encouragement to keep things internal. Make fields private and expose behavior through methods. The newer module system (JPMS, module-info.java) adds a layer above packages, letting a jar declare which packages it exports.

    

    
The fully-qualified name & reverse-domain naming

    
A package turns a short class name into a fully-qualified name (FQN) that is unique across the entire classpath: java.util.List and your own com.acme.List can coexist because their FQNs differ. The convention is to start with your organisation’s domain reversed — you own acme.com, so you own the com.acme package space — which makes collisions between separate vendors essentially impossible. Crucially, the directory layout must mirror the package: the compiler and JVM find a class by translating dots to slashes.

    

    
import: single-type, wildcard, and static

    
You could write every type by its full name, but that is noisy, so import lets you refer to a type by its short name. A single-type import names one class; a wildcard import (import java.util.*;) makes every top-level type of a package available. The wildcard is a pure compile-time convenience — it does not slow anything down and does not bloat your bytecode, because the compiler only pulls in the names you actually reference; nothing is loaded at runtime that you didn’t use. import static brings in members (constants and static methods) so you can drop the class prefix.

    

    
The four access levels, precisely

    
Access is checked at compile time and applies to classes, fields, methods, and constructors. From narrowest to widest: private — only the declaring class (including its nested classes); no modifier — package-private, any class in the same package; protected — same package plus subclasses in other packages; public — every class everywhere. One catch on top-level types: a class can only be public or package-private — private and protected are not legal on a top-level class.

    

    
Package-private as a deliberate encapsulation tool

    
Package-private is not just “the lazy default” — inside a library it is a precise design lever. You can split a feature across several classes in one package, let those classes call each other freely with package-private methods, and expose only the handful of public types you want the outside world to depend on. Callers cannot reach the helpers, so you stay free to rename, split, or delete them without breaking anyone. This is how the JDK keeps implementation classes hidden while shipping a small public surface.

    

    
The classpath: how the JVM finds .class files

    
Packages tell the JVM the relative path to a class; the classpath tells it where to start looking. It is an ordered list of roots — directories and .jar files — and to load com.acme.billing.Invoice the loader searches each root for com/acme/billing/Invoice.class, taking the first match. Set it with the -cp flag or the CLASSPATH variable; build tools like Maven and Gradle assemble it for you. A wrong or incomplete classpath is the classic cause of ClassNotFoundException and NoClassDefFoundError.

    

    
A step above packages: JPMS modules

    
Since Java 9 the module system (JPMS) adds a layer on top of packages. A module-info.java at the root of a jar names the module and declares which packages it exports and which other modules it requires. The key idea is strong encapsulation: a public class in a package that is not exported is genuinely unreachable from other modules — even reflection is blocked by default. It is opt-in; the classic classpath still works, and most applications never write a module-info.java, but the JDK itself is fully modularised.

Coming from another language

    
What will surprise you

      
Coming from Python
Python relies on convention — a leading underscore asks you not to touch it but nothing enforces it. Java's modifiers are compiler-enforced: private genuinely cannot be accessed from outside.

      
Coming from JavaScript
Where JS uses #private fields and module exports, Java uses four access levels plus package structure. Java's default is closed (package-private), whereas a JS module member is private until you explicitly export it — same instinct, different default scope.

      
Coming from Go
Go encodes visibility in capitalization (Exported vs unexported) at the package boundary — effectively just public vs package-private. Java adds protected and private for finer control.

  






  

    
Exercises

    
Make it stick

      
1 · What does no keyword mean?
A field is declared int total; with no access modifier. Who can access it?
💡 Show hint
Any class in the same package — that's package-private, Java's default. It is not public; classes in other packages cannot see it.

      
2 · Least privilege
You're unsure whether a helper method should be public or private. What's the safe default and why?
💡 Show hint
Start private (or package-private). You can always widen access later without breaking callers; narrowing a public API is a breaking change. Keep the public surface as small as possible.

      
3 · Where must the file live?
A class begins with package com.acme.util;. Relative to your source root, what directory and filename must hold it, and what is its fully-qualified name?
💡 Show hint
The directory must mirror the package: com/acme/util/, so a class Strings lives at com/acme/util/Strings.java. Its FQN is com.acme.util.Strings. Dots in the package become slashes on disk.

      
4 · Does a wildcard import cost anything?
Is import java.util.*; slower at runtime, or does it make your program larger, than importing each type by name?
💡 Show hint
No. import is purely a compile-time convenience for writing short names. The compiler resolves only the types you actually reference; nothing extra is loaded at runtime and the bytecode is identical. Single-type imports are often preferred just for readability and to avoid name clashes, not for speed.

      
5 · Hide the helper
You ship a library with a public class Json and a helper Writer in the same package. How do you let Json use Writer while preventing outside code from touching Writer at all?
💡 Show hint
Make Writer package-private (no modifier on the class). Json, being in the same package, can use it freely, but code in other packages cannot even name Writer. With JPMS you get the same effect at module scale by simply not exports-ing the package the helper lives in.
