Call a service the modern way

For years calling HTTP in Java meant the clunky HttpURLConnection or a third-party library. Java 11's java.net.http changed that: a clean, immutable HttpClient with synchronous and async sends, built right into the JDK.

Concept

Client, request, response — with async built in

🏷 Real-world analogy

Think of an HttpClient as a courier company you set up once — you configure its address book, cut-off times (timeouts), and whether it follows forwarding addresses (redirects), then hand it every shipment for the life of your app. An HttpRequest is one addressed parcel: the destination URI, the instruction on the label (GET, POST…), any extra notes (headers), and optionally contents to deliver (a body). A BodyHandler is you telling the courier how to unpack the reply — hand it back as a String, drop it straight into a file, or stream it in as it arrives. You never rebuild the courier company per parcel; you describe each parcel fresh and reuse the same reliable operation underneath.

Build one reusable HttpClient, describe the call with an immutable HttpRequest, then send it (blocking) or sendAsync (returns a CompletableFuture). The response carries a status code and a typed body via a BodyHandler.

Check statusCode() before trusting the body — a 4xx or 5xx still returns normally (no exception). The async path pairs naturally with virtual threads or CompletableFuture chains for calling many services at once. Treat HttpClient like a connection pool: create it once and share it.

    


    
Build the client once, reuse it everywhere

    
An HttpClient is immutable and thread-safe. Configure it once through its builder — HTTP version, redirect policy, connect timeout, a shared connection pool — then share the single instance across your whole app. Under the hood it keeps live connections and, on Java 11+, prefers HTTP/2 (falling back to 1.1). Creating a fresh client per request throws all that reuse away.

    


    
Describe the call with an HttpRequest

    
Each request is built fluently from HttpRequest.newBuilder(uri) and is itself immutable. Pick a method — GET() takes no body; POST, PUT, and DELETE take a BodyPublisher that supplies the request body. Add headers, and set a timeout for this specific call.

    


    
Send synchronously and read the response

    
The blocking send takes the request and a BodyHandler describing how to materialize the body — BodyHandlers.ofString() is the common one. It returns an HttpResponse<String>. Always branch on statusCode() first: a 4xx or 5xx comes back normally, not as an exception.

    


    
Go non-blocking with sendAsync

    
sendAsync returns a CompletableFuture<HttpResponse<T>> immediately, so you can compose the result without parking a thread. Chain thenApply/thenAccept to transform, and fire many calls at once, joining them with CompletableFuture.allOf instead of waiting for each in turn.

    


    
Bodies beyond String

    
The body type is chosen entirely by the BodyHandler, and it isn't limited to strings. Stream large downloads with ofInputStream(), save straight to disk with ofFile(path), or discard the body with discarding(). Note the client does not parse JSON — you take the String (or stream) and hand it to a library like Jackson.

    


    
Why it replaced HttpURLConnection

    
The legacy HttpURLConnection was verbose, mutable, HTTP/1.1-only, and had no real async story — you manually opened streams, set methods reflectively, and read bytes by hand. java.net.http replaces all of it with a fluent, immutable API, native HTTP/2, WebSocket support, and first-class async via CompletableFuture, all in the JDK with no third-party dependency.

Coming from another language

    
What will surprise you

      
Coming from Python
HttpClient is the JDK's answer to requests/httpx. send ≈ a blocking requests.get; sendAsync ≈ httpx's async client. One difference: a non-2xx response doesn't raise — you check statusCode() yourself.

      
Coming from JavaScript
Very close to fetch: build a request, await a response, then read the body. Like fetch, a 404 is a successful call with a 404 status — no exception — so you must inspect the status code explicitly.

      
Coming from C#
Almost a direct port of HttpClient in .NET, down to “create once and reuse.” sendAsync + CompletableFuture ≈ SendAsync + Task. Same advice: don't new up a client per request.

  






  

    
Exercises

    
Make it stick

      
1 · No exception on 404
You call an endpoint that returns 404 and your code reads res.body() as if it succeeded. What did you forget?
💡 Show hint
To check res.statusCode() first. The client returns normally for 4xx/5xx — it doesn't throw — so the body may be an error page or empty. Branch on the status before trusting the body.

      
2 · Sync or async?
You must call 50 independent services and combine the results. Which send method, and why?
💡 Show hint
sendAsync — fire all 50 as CompletableFutures so they run concurrently, then combine. Calling send (blocking) in a loop serializes them, taking the sum of all latencies. (Virtual threads make even the blocking style scale, but async composes the results cleanly.)

      
3 · A client per request
A teammate calls HttpClient.newHttpClient() inside a method that runs on every request. Why is that wasteful, and what should they do instead?
💡 Show hint
Each new client spins up its own connection pool and (for HTTP/2) its own connections, throwing away keep-alive reuse and adding setup cost per call. Since HttpClient is immutable and thread-safe, build one instance (a static field or an injected singleton) and share it across all requests.

      
4 · POST a JSON body
You need to POST {"name":"Ada"} as JSON. Which builder methods set the method, the body, and the content type — and does the client serialize the object for you?
💡 Show hint
Use .POST(BodyPublishers.ofString(json)) and .header("Content-Type", "application/json"). The client does not serialize objects — you produce the JSON string yourself (e.g. with Jackson's ObjectMapper.writeValueAsString) and feed it to the BodyPublisher.

      
5 · Don't buffer a huge download
You must download a 2 GB file. Why is BodyHandlers.ofString() a bad choice here, and what handler fits?
💡 Show hint
ofString() buffers the entire body into memory — 2 GB of heap, likely an OutOfMemoryError. Use BodyHandlers.ofFile(path) to stream it straight to disk, or ofInputStream() to process it in chunks as it arrives.
