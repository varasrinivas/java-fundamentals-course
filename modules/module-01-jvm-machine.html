Your code's real computer

You don't run Java on your laptop. You run it on a machine that doesn't physically exist — the JVM. Understanding that imaginary computer explains almost everything strange about Java: the compile step, "write once run anywhere," startup lag, and why it gets faster the longer it runs.

Concept

Two compilers and an imaginary machine

🏭 Real-world analogy

The JVM is a stage crew running a play that tours the world. The playwright writes one script (your .java source). A translator (javac) turns it into a universal stage-notation (bytecode) that any theatre understands — not tied to one building. Each venue has its own local stage crew (the JVM for that OS + CPU): they read the same notation, so the identical script plays in Tokyo, Berlin, or a phone screen without a rewrite — that is “write once, run anywhere.” The crew starts by reading the notes aloud line-by-line (the interpreter), but once they notice a scene runs every night, they rehearse it into muscle memory (the JIT compiler emitting native code) so it flies. That rehearsal is why a Java program is sluggish at curtain-up and faster by Act Three.

In Python or JavaScript, your source is handed more-or-less directly to an interpreter. In Go or C++, it's compiled all the way down to native machine code for your CPU. Java sits in the middle, and that middle is the whole point.

Java is compiled twice. First, javac turns your .java source into bytecode — a compact instruction set for a CPU that was never manufactured. Then the JVM (Java Virtual Machine) loads that bytecode and, while the program runs, a Just-In-Time (JIT) compiler translates the hot parts into real native code on the fly.

Because bytecode targets the imaginary machine and not your CPU, the same .class file runs unchanged on Windows, macOS, Linux, ARM, or x86 — as long as a JVM exists for that platform. That's "write once, run anywhere," and it's a property of bytecode, not magic.

The closest cousin

.NET works almost identically: C# compiles to IL (bytecode), which the CLR runs with its own JIT. If you know the CLR, you already understand the JVM's shape — just swap the names.

The spec vs the implementation: HotSpot and friends

“The JVM” is really two things. There is the Java Virtual Machine Specification — a document describing the .class file format and how each bytecode instruction must behave — and there are implementations of that spec you actually download and run. The dominant one is HotSpot, the VM inside the OpenJDK reference codebase. Vendors build and ship OpenJDK under their own names (Eclipse Temurin, Amazon Corretto, Azul Zulu, Oracle JDK); they are the same core code, differing mostly in support and packaging. Others exist too, like Eclipse OpenJ9, tuned for lower memory.

Because the spec is what matters, code compiled against one JDK runs on any conforming JVM of a compatible version. You can inspect which one you have:



    
Class loading: how a .class becomes a live type

    
The JVM does not read your whole program up front. It loads each class lazily, the first time that class is actually needed, in three phases: loading (find the .class bytes and create a Class object), linking (verify the bytecode is well-formed and safe, prepare static fields, resolve references), and initialization (run static initializers and static field assignments). Verification is a real security and stability feature: hand-crafted or corrupt bytecode that would corrupt the stack is rejected before a single instruction executes.

    
Class loaders form a parent-first delegation chain — the bootstrap loader (core java.* classes), then the platform and application loaders — so your own class can never shadow java.lang.String.

    


    
The JIT: interpret first, compile the hot paths

    
A fresh JVM interprets bytecode — walking instructions one at a time. That starts instantly but runs slowly. Meanwhile the JVM profiles execution, counting how often each method runs and which branches are taken. When a method crosses a “hotness” threshold, the JIT compiler translates it to optimized native code in the background, and future calls jump straight to that native version. HotSpot uses tiered compilation: the C1 compiler produces decent code fast for quick wins, and the heavier C2 compiler later re-compiles the hottest methods with aggressive optimizations (inlining, loop unrolling, dead-code elimination) using the profile data.

    
This is why the same loop can speed up mid-run, and why serious benchmarks “warm up” the JVM before measuring. You can watch it happen:

    


    
Runtime data areas: where your program lives

    
While it runs, the JVM carves memory into distinct regions defined by the spec. The heap is the shared pool where every object lives and where the garbage collector works. Each thread gets its own JVM stack of frames holding local variables and partial results (blow past its limit with runaway recursion and you get a StackOverflowError). The PC register per thread tracks which instruction is executing. Class metadata — the loaded bytecode, field and method info — lives in Metaspace, which since Java 8 sits in native memory rather than the old fixed-size “PermGen.”

Not just Java: the JVM is a shared platform

    
The JVM runs bytecode, and it does not care which language produced it. That has made it a host for a whole family of languages that compile to .class files and interoperate with Java libraries: Kotlin (the default for Android, concise and null-safe), Scala (functional + object-oriented, powers Spark), Groovy (dynamic, the language of Gradle build scripts), and Clojure (a Lisp). You can even mix them in one project because they all share the same object model at runtime.

    


    
The toolbox: javac, java, and jar

    
Three command-line tools cover the everyday lifecycle. javac compiles .java sources to .class bytecode. java launches a JVM and runs a class's main method (note you name the class, not the file — no .class suffix). jar bundles many .class files plus a MANIFEST.MF (which can name the entry-point class) into one shippable .jar archive — really just a ZIP.

Coming from another language

    
What will surprise you


    

      Coming from Python
      
There's no "just run the file." You must compile first (javac Hello.java)
      then run the result (java Hello). CPython also makes bytecode (.pyc),
      but hides it. Java makes it explicit — and ships that bytecode, not your source.

    


    

      Coming from JavaScript
      
V8 already JITs your JS, so the "gets faster as it runs" idea is familiar. The difference: Java has a
      real, separate compile step with type checking up front. Many bugs that are runtime
      TypeErrors in JS are caught by javac before the program ever starts.

    


    

      Coming from Go
      
Go compiles straight to a single native binary — no VM, instant startup. Java trades that for
      portability and a world-class JIT: a long-running Java service can hit throughput a static binary
      struggles to match, at the cost of slower cold starts and a runtime to ship.

    


    

      Coming from C#
      
You're basically home already. javac ≈ Roslyn, bytecode ≈ IL, JVM ≈ CLR,
      JAR ≈ assembly. The biggest day-one differences are tooling (Maven/Gradle vs MSBuild) and that Java's
      checked exceptions have no C# equivalent.

    

  







  

    
Exercises

    
Make it stick


    

      
1 · Predict the commands

      
You have Greeter.java containing a class named
      Greeter. Write the exact two terminal commands that compile it and then run
      it. What new file appears after the first command?

      

        💡 Show hint
        
Compile with javac Greeter.java — this produces
        Greeter.class (the bytecode). Run with java Greeter
        (note: no .class extension — you name the class, not the file).

      

    


    

      
2 · Why is the second run faster?

      
A teammate benchmarks a tight loop and notices it runs slowly for the first few
      thousand iterations, then suddenly speeds up — within the same program run. No code changed.
      What happened?

      

        💡 Show hint
        
The JVM starts by interpreting bytecode. Once it sees a method
        is "hot" (called often), the JIT compiler translates it to optimized native code,
        and subsequent iterations run at near-native speed. This warm-up is why JVM benchmarks discard the
        first runs.

      

    


    

      
3 · One JAR, many machines

      
You build a .jar on your x86 Windows laptop and email it to a
      colleague on an ARM Mac. It runs without recompiling. In Go, the same trick fails. Explain the
      difference in one sentence.

      

        💡 Show hint
        
The JAR contains bytecode for the platform-independent JVM, so
        any JVM can run it; a Go binary contains native machine code compiled for one
        specific OS + CPU architecture.

      

    


    

      
4 · When does static code run?

      
A class Config has a static { ... } block that prints a line. Your main never references Config at all. Does the block run? Now you add one line that reads Config.PORT. Does it run now, and how many times?

      

        💡 Show hint
        
Classes load lazily. If nothing ever touches Config, it is never loaded and the block never runs. The first reference (Config.PORT) triggers loading, linking, and initialization — the static block runs exactly once, no matter how many times you use the class afterward.

      

    


    

      
5 · HotSpot in the version string

      
You run java -version and the last line says OpenJDK 64-Bit Server VM ... (build ..., mixed mode). What does “mixed mode” tell you about how your bytecode will execute?

      

        💡 Show hint
        
“Mixed mode” means the JVM will both interpret bytecode and JIT-compile hot methods to native code — the normal, fast setup. (Pure -Xint interpreted mode or fully compiled modes exist but are rare.) “Server VM” identifies the HotSpot implementation with the C2 compiler enabled.

      

    


    

      
6 · Kotlin on the same VM

      
A colleague compiles a Kotlin file with kotlinc and hands you the resulting .class file. Can your plain java launcher run it? Can your Java code call into it? Why?

      

        💡 Show hint
        
Yes to both. The JVM executes bytecode and does not know or care what language produced it. Kotlin compiles to the same .class format and shares the JVM's object model, so java runs it and Java code can call Kotlin classes (and vice versa) as ordinary JVM types.
